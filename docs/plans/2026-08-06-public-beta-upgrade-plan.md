# 灵感来袭 2.0 公开 Beta 全面升级实施计划

**状态**：历史实施计划；2.0/2.1 已完成主要基础项，未完成内容以当前原则对照重新排期<br>
**对应 PRD**：`docs/product-upgrade-prd.md`<br>
**目标版本**：`2.0.0-beta.1`

> 当前长期原则见 `docs/PROJECT-PRINCIPLES.md`；截至 2026-08-14 的缺口与后续顺序见 `docs/plans/2026-08-14-principles-gap-analysis.md`。本文件保留当时决策背景，不再作为当前完成状态清单。

## 1. 实施原则

1. 先安全和数据，再体验和功能，最后分发和推广。
2. 保留当前工作区已有改动，不重写无关模块。
3. 每个阶段都必须有可独立验证、可回滚的产物。
4. 数据迁移先在副本运行；任何失败不得覆盖用户源数据。
5. 不以新增平台数量作为进度指标。

## 2. 现状基线

- 顶层 `npm run check` 通过：classifier、entries、fetcher、store。
- GitHub、Bilibili、Readability 三个嵌套 scraper 测试通过。
- GitHub scraper 测试存在 `MaxListenersExceededWarning`。
- 当前 CI 未执行嵌套 scraper 测试，并重复运行顶层测试。
- 工作区存在 README 视觉升级和钉钉 Stream 接入的未提交改动，实施时必须保留。

## 3. 里程碑总览

| 里程碑 | 目标 | 发布判断 |
| --- | --- | --- |
| M0 基线冻结 | 固定回归样本、数据夹具和风险清单 | 可以安全开始改造 |

## 4. Phase 0：基线与风险隔离

### 4.1 测试基线

**工作项**

- 新增代表旧版数据的迁移夹具，包含：分类、最高编号删除、孤立档案、截图、正文和特殊字符。
- 为所有现有 API 建立成功、非法输入和未授权用例。
- 增加浏览器主流程测试：加载、空态、新增、状态、笔记、删除/归档、恢复。
- 将嵌套 scraper 测试纳入统一测试入口，区分离线单元测试和联网集成测试。
- 处理 GitHub scraper 的监听器告警。

**涉及模块**

- `scripts/run-tests.js`
- `.github/workflows/ci.yml`
- `lib/*.test.js`
- `lib/scraper/*.test.js`
- 新增 `test/fixtures/` 和 API/浏览器测试目录

**验收**

- `npm run check` 不访问真实用户数据。
- CI 在 Node.js 20/22 上执行一次完整离线测试。
- 联网测试单独运行，网络失败不会伪装为代码回归。

### 4.2 数据格式设计

**决策**

- 展示编号继续用于可读性，但新增稳定 `uid` 作为内部标识。
- `DATA.md` 保持人类可读，在条目中增加机器可解析、不会影响渲染的元数据。
- 数据文件增加格式版本；首次启动检测版本并决定是否迁移。

**候选格式**

```markdown
<!-- linggan:data-version=2 -->

### ⏳ 1.1 示例标题
<!-- linggan:uid=01J... -->
- **简介**：...
```

最终格式必须通过“手工编辑后仍可恢复”的测试，不依赖字段顺序或脆弱的单一正则。

## 5. Phase 1：可信数据底座

### 5.1 稳定主键与迁移器

**工作项**

- 新增 `lib/schema.js`：格式版本、条目元数据解析和序列化。
- 新增 `lib/migrate.js`：扫描、预检、备份、迁移、校验和回滚。
- 研究档案目录从展示编号映射到稳定 uid；保留兼容索引。
- 迁移日志仅记录结构和结果，不记录敏感正文。

**验收**

- 删除最高编号后新增条目不会读取旧档案。
- 重复运行迁移不会重复修改数据。
- 任一步骤失败时源数据字节级保持不变。

### 5.2 写入服务

**工作项**

- 新增 `lib/writequeue.js`，所有数据写操作串行执行。
- 将读取—修改—写入封装为单一事务接口。
- 增加 URL 规范化和重复检测。
- 备份名称与 `DATA.md` 一致，并保留时间戳而不是每天覆盖一次。
- 增加写入后解析校验，失败自动回滚。

**验收**

- 20 个并发新增请求不会丢条目或产生重复 uid。
- 模拟写入失败后原文件和最近有效备份可用。
- 重复 URL 返回明确的已有条目信息。

### 5.3 回收站与档案生命周期

**工作项**

- 普通删除改为归档到回收站。
- 研究档案、截图和正文与条目 uid 绑定。
- 提供恢复和永久删除；永久删除二次确认并生成最终备份。
- 扫描并提示现有孤立档案，不自动删除。

## 6. Phase 2：安全边界

### 6.1 本地 API 认证

- 启动时生成或读取本地访问令牌。
- 非本机访问默认拒绝；如显式开启，所有普通 API 必须认证。
- 浏览器会话通过安全的本地引导获得会话令牌，不把长期凭据写入 URL。
- 增加 CSP、点击劫持防护、MIME 嗅探防护和合理的缓存策略。

### 6.2 外部消息入口隔离

- 企业微信、钉钉统一调用受限的 `captureService.addUrl()`。
- 回调只能新增链接，不能读取、恢复、删除或浏览研究档案。
- 企业微信继续校验签名；钉钉验证 SDK 事件来源和回调目标。
- 推荐独立回调端口或独立反向代理路径，避免把主服务整体暴露给公网隧道。

### 6.3 请求保护

- JSON 和 multipart 请求体统一设置大小上限。
- 写接口增加本地速率限制。
- 日志对 token、Secret、URL 查询敏感字段做脱敏。
- 安全文档明确网络请求、消息平台和公网隧道的数据流。

## 7. Phase 3：核心产品体验

### 7.1 信息架构

- 产品主导航收敛为：收件箱、研究中、已完成、归档。
- 分类和标签成为整理维度，不与流程状态混用。
- 新收藏默认进入收件箱，自动分类显示为建议。
- “难度”升级为可选的“预计投入”。

### 7.2 研究模板

新增模板：

1. 通用研究：为什么收藏、关键发现、行动项、结论。
2. 文章阅读：摘要、重要观点、摘录、反思。
3. 视频学习：时间点、知识点、实践任务。
4. 项目调研：用途、技术栈、采用风险、结论。
5. 软件评测：保留现有下载安装、体验和收藏判定字段。

模板层应放在独立模块，前端只负责呈现 schema，不继续在 HTML 中硬编码所有字段。

### 7.3 搜索与整理

- 标题、摘要、来源、分类、标签即时搜索。
- 笔记和正文建立本地搜索索引。
- 支持组合筛选和清除筛选。
- 搜索结果显示命中位置和内容类型。

### 7.4 首次使用与一致性

- 修复“选择文件”和“新增第一条”空态行为。
- 完成 `README.md` → `DATA.md` 文案清理。
- 增加启动检查页：数据路径、备份状态、网络能力、可选入口状态。
- 错误提示提供原因、影响和下一步操作。
- 对窄屏、键盘、焦点管理、对比度和减少动画偏好进行验证。

## 8. Phase 4：数据自主与采集入口

### 8.1 数据管理

- 导出完整数据包：`DATA.md`、档案、截图、正文和版本清单。
- 从完整数据包恢复，恢复前展示预检结果。
- 支持浏览器书签 HTML 导入，其他服务导入后续按需求增加。
- 提供可下载的匿名诊断包，默认不含用户正文和凭据。

### 8.2 快速采集

- 第一优先：Bookmarklet，低维护、可快速验证。
- 第二优先：浏览器扩展，支持当前页一键保存和可选标签。
- 企业微信/钉钉作为高级可选入口，不出现在首次使用主流程。

## 9. Phase 5：Windows 分发

### 9.1 最小可行路径

- 强化 `start.bat`：环境检测、端口检测、错误日志位置和升级提示。
- 提供版本化发布压缩包，避免用户从源码工作区运行。
- 评估 Node 单可执行应用或轻量包装；只有在更新和数据目录策略明确后再制作安装器。

### 9.2 数据目录

- 程序文件与用户数据分离。
- Windows 用户数据默认放在明确且可备份的位置。
- 卸载程序默认不删除用户数据。
- 升级程序执行迁移前必须展示备份位置。

### 9.3 验收矩阵

- Windows 10/11。
- 全新安装、覆盖升级、离线启动、端口占用、无网络、代理环境。
- 中文路径、空格路径、非管理员账户。

## 10. Phase 6：公开 Beta 发布

### 10.1 发布资产

- 只读在线 Demo，明确标注不包含本地服务能力。
- 60 秒主流程演示视频/GIF。
- Windows 快速开始、完整安装、数据迁移和卸载指南。
- 隐私说明、安全模型、已知限制和故障排查。
- `CHANGELOG.md`、Git Tag、GitHub Release 和校验值。

### 10.2 反馈机制

- Bug、功能建议、数据恢复三类 Issue 模板。
- 应用内“导出诊断信息”入口。
- 首批招募 20-50 名技术研究者，完成规定任务后访谈。

### 10.3 Beta 任务脚本

1. 安装并启动。
2. 保存一个 GitHub、一个文章和一个 B站链接。
3. 处理重复链接。
4. 为一个条目填写研究结论。
5. 导出备份并执行恢复演练。

## 11. 测试与发布门禁

每次阶段合并必须执行：

```bash
npm run check
```

并根据改动执行：

- 数据迁移与回滚测试。
- API 认证和安全测试。
- 浏览器端到端测试。
- 三类 scraper 离线夹具测试；联网冒烟测试单独记录。
- Windows 分发验证。
- 最终 `git diff` 和用户数据泄露检查。

禁止用“手工看起来正常”替代迁移、安全和恢复自动化测试。

## 12. 建议实施顺序

1. M0 测试基线与数据格式 RFC。
2. M1 稳定主键、迁移器、写入队列、回收站。
3. M2 API 安全与消息入口隔离。
4. M3 收件箱、标签、模板、搜索和首次使用。
5. M4 导入导出、完整备份和诊断。
6. M5 Windows 分发。
7. M6 小范围公开 Beta。

在 M1 和 M2 完成前，不继续扩张新的外部接入平台；在 M3 的真实用户激活得到验证前，不启动云同步或团队协作设计。
