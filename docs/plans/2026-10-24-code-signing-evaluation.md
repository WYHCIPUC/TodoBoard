# 代码签名评估

**日期**：2026-10-24<br>
**对象**：`linggankanban-*-windows-x64.exe` 与便携包<br>
**结论**：当前阶段不购买证书；达到商业交付阈值后再启用 OV/EV 或云签名，并把签名验证纳入发布门禁。

## 当前状态

- EXE 由本仓库 `scripts/build-executable.ps1` 生成，使用固定 Node.js 24.16.0 win-x64 运行时与 .NET 自包含启动器。
- 未使用商业代码签名证书；Windows SmartScreen 可能对首次下载显示“未知发布者”。
- 发布说明已要求只从本仓库 Release 下载并核对 `SHA256SUMS.txt`。
- 代码签名与“数据可信恢复”无关：签名证明发布者与二进制完整性，不替代本地备份、快照和恢复演练。

## 选项与成本量级

| 方案 | 年成本量级 | 信任建立 | 运维复杂度 | 适用阶段 |
| --- | --- | --- | --- | --- |
| 不签名 + SHA-256 + GitHub Release | 0 | 依赖仓库信誉与哈希核对 | 低 | 开源 Beta、内部试用 |
| OV 代码签名证书 | 约数百美元 | 减少“未知发布者”，SmartScreen 仍需声誉积累 | 中：证书保管、时间戳、CI 密钥 | 有稳定外部下载量 |
| EV 代码签名证书 | 约数百至上千美元 | 更快建立 SmartScreen 信誉 | 高：硬件令牌/云 HSM、双人审批 | 付费商业交付、企业采购 |
| Azure Trusted Signing 等云签名 | 按量/订阅 | 与 OV/EV 类似，取决于配置 | 中：云端身份与 CI 集成 | 长期自动化发布 |

具体报价随 CA、证书类型、硬件令牌和地区变化；采购前需重新询价，不在本文件写死供应商价格。

## 决策阈值

满足以下任一条件再启动采购：

1. 连续两个版本的外部下载量超过约 1,000 次，且出现可复现的 SmartScreen/杀毒误报支持请求；
2. 出现付费支持、企业部署或采购流程要求“已知发布者”；
3. 发布资产需要由多人协作构建，必须用签名绑定发布者身份与构建流水线。

未达到阈值时，继续保持不签名，但必须：

- 发布资产只由 CI 或可复现的本地脚本生成；
- 每次发布附 `SHA256SUMS.txt`，并在 Release 说明中给出校验命令；
- 在 README 与 Release 中明确“未签名”的风险与下载来源；
- 保留两次确定性构建比对结果。

## 启用后的最低要求

- 使用受支持的时间戳服务，签名在证书到期后仍可验证；
- 私钥不进入仓库、构建日志或普通 CI 变量；使用硬件令牌/云 HSM 与最小权限；
- CI 签名步骤只接受受保护的 release 分支/tag，禁止 PR 构建使用生产证书；
- 发布前执行 `signtool verify /pa /all` 并保存输出；
- 同时保留 SHA-256 与签名验证，两者不能互相替代；
- Windows 10 与 Windows 11 各做一次干净账户安装/启动/卸载验证。

## 当前建议

**暂不购买**。当前项目仍以开源、本地优先和可复现构建为主要信任来源；在没有稳定商业下载量或采购要求前，签名成本与私钥运维风险高于收益。把本文件作为下一轮商业交付评审的输入，而不是已采购承诺。
