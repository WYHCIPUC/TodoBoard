# 灵感工作台 v2.2.0 可信恢复与回顾升级计划

**状态**：可执行草案，尚未开始实现<br>
**目标版本**：2.2.0<br>
**制定日期**：2026-08-14<br>
**评估基线**：`package.json` 2.1.0；Git `a4c27f6` 加当前未提交改动<br>
**依据**：[项目原则](../PROJECT-PRINCIPLES.md) · [原则对照与补强计划](2026-08-14-principles-gap-analysis.md)

## 1. 版本目标

v2.2.0 不继续扩张抓取平台，而是补强当前闭环中最弱的四处：

1. 完整备份可以自证，导入失败或进程中断后自动回到最近有效状态。
2. 长期未研究、归档受阻、研究停滞和到期回顾的条目能够重新进入视野。
3. 自动重抓不能用明显更差的新结果覆盖已有好正文，归档损坏可以在不联网时发现。
4. 数据、浏览器主流程和 Windows 成品由自动化门禁共同约束。

版本完成后，产品应从“能够保存和研究”前进到“能够恢复、重新浮现并持续回顾”。

## 2. 成功定义

| 结果 | 可执行验收 |
| --- | --- |
| 恢复可信 | 对暂存、快照、每次目录交换和提交后校验逐点注入故障；结果只能是完整旧态或完整新态，不能是混合状态。 |
| 备份自证 | 任意文件被篡改 1 字节、缺失、重复或大小不符时，均在写入活动数据前拒绝。 |
| 旧数据诚实 | 历史条目没有可信时间时显示“日期未知”，不把升级时间伪装成创建时间。 |
| 待处理可解释 | 每条结果展示命中原因、阈值和排序依据，并可打开、延后或完成相应动作。 |
| 正文不倒退 | “成功但低质量”的候选正文未通过质量门禁时，活动正文 SHA-256 保持不变。 |
| 状态无请求风暴 | 1000 条固定夹具下，看板首次读取归档状态只发送 1 个批量状态请求。 |
| 本地检查不出站 | 完整性扫描中的任何网络调用都会让测试立即失败。 |
| 成品可发布 | Node 22/24、Chromium 主流程和 Windows EXE smoke 全部通过后，才允许创建稳定标签。 |

## 3. 范围与非目标

### 本版包含

- 完整备份格式 v2、SHA-256 清单、严格预检、维护锁、事务导入和崩溃恢复。
- 生命周期时间注释、待处理规则、只读聚合 API 和现有界面内的待处理入口。
- 归档候选暂存、质量比较、目录级提交、manifest、本地完整性扫描和批量状态 API。
- 受影响模块的故障注入、真实浏览器测试、Windows 构建 smoke 与发布门禁。

### 本版不包含

- 新增微信个人号自动化、抓取平台、云同步、账号、多端实时同步或多人协作。
- 头脑风暴方案的“待验证 / 已验证 / 被否定”反馈闭环；列入 2.3 候选。
- 强制 AI、API Key、遥测、设备绑定或联网授权。
- 更换前端框架、一次性拆完 `board.js` / `board.css`、搜索缓存和成功队列压缩。
- 安装器、代码签名或消除所有 SmartScreen 提示；发行说明继续如实披露未签名风险。

## 4. 已确认的现状

- v1 备份包含 `DATA.md` 和白名单内的条目档案，不含已保存头脑风暴、回收站或运行队列；导入中途失败只报告备份位置，不自动回滚。
- 迁移副本会保留条目目录中的普通附件，v1 完整备份却会静默跳过它们；v2 必须统一这两个“完整数据”口径。
- 50 MiB 解码后上限只在遍历条目文件时检查；仅有超大 `DATA.md` 时可能绕过。当前没有文件数、重复路径、声明大小或 checksum 校验。
- `DATA.md` 格式版本为 2，条目由标题、稳定 UID 注释和 `- **字段**：值` 组成；当前没有生命周期时间。
- “今日推荐”只按待研究、难度和编号选择；前端会为 N 条记录并发发送 N 个归档状态请求。
- 归档会逐个写入活动目录。空正文或明确降级会保留旧正文，但“标记成功、质量更差”的正文仍可能覆盖旧版；元数据没有文件 checksum。
- CI 当前只在 Ubuntu 的 Node 20/22 执行 `npm run check`。现有 UI 测试以源码合同为主，Windows 成品 smoke 尚未进入 CI。

这些是设计输入，不代表本计划中的目标已经实现。

## 5. 关键决策

### D1. 完整备份升级为 v2，数据 Markdown 保持 v2

备份格式升级是破坏性合同变化，必须使用 `version: 2`。生命周期注释则是 2.1 会忽略并保留的加法扩展，因此不提升 `<!-- linggan:data-version=2 -->`。这样 2.2 的活动数据仍可由 2.1 读取，保留降级路径。

### D2. 用户备份与运行状态分开

v2 默认包含：

- `DATA.md`；
- 活动条目的笔记、正文、截图、归档产物和 `attachments/**` 普通附件；
- 每个条目由 2.2 写入并验证的最近一份 `protected-generations/**` 正文保护代；
- 尚未提交完成的内容寻址人工正文 `drafts/manual-<sha256>.md` 及同名 `.json` 元数据；
- `.linggan/brainstorms/*.md` 已保存方案；
- `.linggan/trash/` 中的记录及其档案；
- 正常迁移或删除留下的旧编号目录、孤立档案和其他普通文件，以 `orphans/**` 只读恢复范围保存。

继续排除：归档队列及 `.previous`、审计和错误日志、迁移/事务备份、缓存、临时文件、令牌、Cookie、消息平台凭据、浏览器偏好和 IndexedDB 副本。排除队列的前提是队列不再保存唯一用户正文：每次人工补录先按内容 SHA-256 写入不可变 `drafts/manual-<sha256>.md` 与 `{version:1,uid,sha256,createdAt,origin:'manual'}` JSON，两个文件均 fsync/复读后 HTTP 才返回已接收；同内容复用，不同内容并存。队列只保存 UID、不可变路径和 hash 引用，归档提交成功后只成对删除它实际消费的该 hash `.md/.json`，绝不覆盖其他待处理草稿。

成功提交导入（包括启动时确认 `committed`）后原子清空旧运行队列，不从备份或归档状态推断新的联网任务；导入出的人工草稿显示为 `manual_pending`，由用户继续提交，不自动联网。其他未归档条目进入待处理中心，由用户显式重试。回滚到旧态则恢复导入前队列及其原有调度，不新增任务、不改变其既有联网语义。

首次 2.2 升级必须在清理旧队列前扫描 `archive-jobs.json`：发现 `manualContent` 时先按 UID 与完整内容 hash 写入上述不可变草稿；相同则复用，不同则并存并标记多个 pending，绝不覆盖任一版本；找不到活动 UID 的正文进入 `recovered-orphans/legacy-manual-drafts/`。只有每段人工正文都有已 fsync 且复读 hash 一致的受备份副本后，才允许移除队列中的正文。契约测试同时提交同 UID 两段不同正文并在每个持久化点崩溃，恢复后两个 hash 都必须存在。

未知文件不能静默丢失：允许的 `attachments/**` 留在所属条目；其他普通文件和孤立目录中的内容映射到 `orphans/**`，恢复到 `.linggan/recovered-orphans/<transactionId>/`，不执行、不解析、不放回活动档案。符号链接、设备和其他特殊文件使导出失败并列出路径。空目录不视为用户内容，按需重建。

导出也通过同一维护协调器取得一致性读快照：收集和计算清单期间暂停用户数据写入，成功或失败后立即释放；不得把不同时间点的 `DATA.md` 与档案拼成一个包。

SHA-256 用于发现意外损坏和内容不一致，不是数字签名，也不提供来源真实性或保密性。备份仍是明文用户数据，导出和导入确认页必须提示妥善保存。

### D3. v1 可读，范围外数据不被旧备份删除

v2.2 同时导入 v1 和 v2。v1 先转换为内部清单，替换 `DATA.md`，并仅以 overlay 方式覆盖包中实际列出的历史白名单文件；同 UID 未列出的截图、归档文件、`attachments/**`、`drafts/**` 和其他普通文件原样保留。头脑风暴、回收站和 recovered-orphans 根目录不参与替换。已不在导入后 `DATA.md` 中的当前条目目录整体转入 `recovered-orphans/<transactionId>/removed-entries/`。commit 在锁内把这些范围外数据重新 rebase 到 stage；prepare 记录全范围指纹，commit 不一致就要求重新预览，不能把陈旧保留集覆盖回去。预览明确提示“旧备份只覆盖列出的旧格式文件，其余本地数据继续保留”。v2.1 无法导入 v2，此单向限制写入界面和发行说明。

### D4. 导入采用同卷暂存、journal 和 rename-swap

维护锁只覆盖取得一致快照和交换活动数据的窗口，不能从“预览确认”一直锁到用户点击。所有多文件写操作从开始到完成持有共享 mutation lease；导出、prepare 指纹和 commit 获取独占 lease，并等待已有 lease 结束。提交和导出还会暂停归档队列并等待当前 worker 完整结束，最长 60 秒；超时就在活动数据未改变前中止，不强杀 worker。

锁必须落在共享服务层，而不是只拦 HTTP 路由：`store.mutate()`、研究档案/截图、回收站、头脑风暴保存、采集的“保存 + 入队”和归档提交都接入同一个 `lib/maintenance.js` 协调器，企业微信和钉钉入口也不能绕过。嵌套调用传递同一个 lease token，不能重复获取造成死锁。

commit 的多根交换无法做到单个文件系统原子操作，因此交换窗口内除静态恢复界面、`/api/health` 和 `/api/recovery/*` 外，所有数据读写 API 都返回 `503 Service Unavailable`、`Retry-After: 2` 和 `code: maintenance_mode`。`GET /api/entry` 必须拆出真正无副作用的只读实现；不能再把创建模板的读取伪装成只读。

1. prepare 阶段纯内存验证格式、路径、大小、UID、清单和 checksum；短暂取得一致性读锁并记录当前用户数据指纹，不写活动目录。
2. 在 `.linggan/import-transactions/<id>/transaction.json` 写协调 journal，并在每个活动目标的同目录创建 `<name>.import-<id>.stage`；落盘后重新读取校验，此时不长期持有维护锁。
3. commit 阶段获取维护锁、暂停队列，重新计算当前数据指纹、大小、目标卷空间和事务状态；用户数据在确认前后发生变化时返回 `state_changed`，要求重新预览，不能静默覆盖新改动。
4. 校验锁定时刻的活动数据；`live → <name>.import-<id>.old` 这次同卷 rename 本身建立完整回滚快照，不再复制第二份 current。
5. 按 journal 执行每个根的 `live → old`、`stage → live`，每一步落盘事务状态。
6. 校验新活动数据后提交；失败则逆序恢复并再次校验。
7. 启动时先处理未完成提交，再执行数据迁移和创建归档服务；`capture` 改为延迟初始化且队列以 `autoStart: false` 创建。仅完成 prepare 的事务超过 24 小时后安全清理。

每个目标卷都单独预检，stage 和 old 都与对应活动目标同卷，禁止跨卷 rename。prepare 前所需新增可用空间为“该卷 stage 字节 + `max(64 MiB, 该卷 current 与 stage 之和的 10%)`”；commit 时 stage 已占用，只重新确认安全余量仍存在。old 由现有 live 改名，不重复占用 current 字节。成功事务的 old 快照保留 7 天且最多 2 组；最新一组在 7 天内不自动删除，用户可在数据管理中提前删除。

本版限制固定为：全包解码后最多 50 MiB、序列化 JSON 最多 80 MiB、最多 5000 个文件、单个普通附件最多 20 MiB；截图 5 MiB、归档图片 10 MiB、原始 HTML 解压后 20 MiB 的既有限制继续生效。所有文件载荷统一使用 Base64，导出在发送前同时测量解码总量和最终 JSON UTF-8 字节数，因此任何成功导出的包都能被同版本导入。恰好等于上限允许，超 1 字节拒绝。超限时不生成残缺包，并引导用户直接复制数据目录；流式大备份留到后续版本。

`raw.html.gz` 的 checksum 覆盖压缩字节，文件记录另含 `uncompressedBytes`。验证使用带硬上限的流式 gunzip，输出超过 20 MiB 立即中止，不能先无界解压到内存。非法或超限 gzip 从 v1 进入 `orphans/corrupt-archive/**`，不放入活动归档。

### D5. 生命周期使用可忽略的 UTC 注释

```markdown
### ⏳ 1.1 示例
<!-- linggan:uid=11111111-1111-4111-8111-111111111111 -->
<!-- linggan:created-at=2026-08-14T08:00:00.000Z -->
<!-- linggan:last-studied-at=2026-08-15T09:30:00.000Z -->
<!-- linggan:next-review-at=2026-09-14T09:30:00.000Z -->
```

- JS 对外字段为 `createdAt`、`lastStudiedAt`、`nextReviewAt`；磁盘键沿用 kebab-case。
- 时间必须是规范 UTC ISO 8601 毫秒格式；显示时转换为本地时区。
- 新条目在首次持久化时只写一次 `createdAt`。旧条目保持 `null`，不得根据文件 mtime、编号或迁移时间推断。
- `lastStudiedAt` 在开始研究、完成状态、保存非空研究内容或明确点击“已回顾”后更新；仅打开、计时、抓取和重试不更新。
- 转为完成且没有未来计划时，默认设置 30 天后的 `nextReviewAt`；重新设为待研究时清空，用户也可延后或清除。
- 未知注释原样保留；重复或非法时间进入健康诊断，不静默修正。

独立档案保存采用“正文优先”语义：先保存 `notes.md`，再更新时间。若后者失败，响应必须明确返回 `saved: true, lifecycleUpdated: false`，不能把已保存笔记误报为丢失。

### D6. 待处理中心是现有工作区的过滤入口

不新增第三个一级产品空间。在“灵感来袭”工具区增加“待处理 N”，复用现有列表、档案、状态和归档操作。纯逻辑模块 `lib/attention.js` 只读本地文件，不调用会创建模板的 `entries.getEntry()`，也不发网络请求。

默认规则：

| 原因码 | 命中规则 | 优先级 |
| --- | --- | --- |
| `archive_blocked` | `failed`、`manual_required`、`manual_pending`、无在途任务的 `not_archived`，或没有可用正文 / 可重试 / 完整性损坏的 `partial` | 1 |
| `review_due` | `nextReviewAt <= now` | 2 |
| `open_action` | 研究档案有非空行动项且条目未完成 | 3 |
| `stalled` | 进行中且最近可信研究活动超过 14 天 | 4 |
| `unresearched` | 待研究、创建超过 7 天且研究要点仍为空或占位 | 5 |
| `lifecycle_missing` | 历史条目没有可信时间；只提示整理，不声称逾期 | 6 |

同一条目可以有多个原因。先按最高优先级，再按逾期最久、最近活动最早、数字编号升序。只因缺少可选 raw HTML 或图片而 `partial` 的条目不进入待处理中心。“今日推荐”复用同一可行动排序，但排除只有归档故障或日期未知的条目。

### D7. 归档以最近有效正文为底线

v2.2 先统一正文事实源：`entries/<uid>/archive/content.md` 是唯一可写、可读的 canonical 正文。新增无队列副作用的 `lib/archive-content.js` reader；`/api/entry/scrape` 改为调用 ArchiveService 的显式刷新，不再调用会无条件覆盖根级 `content.md` 的 `entries.saveContent()`；正文 GET、人工补录、`lib/search.js` 和 `lib/brainstorm.js` 全部改走同一 reader/service，正常运行时不再回退根级正文。

首次启动 2.2 的升级迁移阶段、在数据 API 和归档队列启用前执行可恢复转换：仅有根级 `content.md` 且正文可用时，将其作为 `legacy_unknown` 候选纳入归档；两处正文都存在且内容不同时，保留现有归档为活动版，把根级正文移入 `attachments/legacy-content-<hash>.md`，记录 `legacy_content_conflict` 并让用户后续选择，绝不自动覆盖。迁移成功并校验前不删除根级文件，普通 GET 不承担迁移副作用。

新增纯逻辑 `lib/archive-quality.js`，候选全部写入活动目录旁的唯一 staging；候选完整校验前，活动 `archive/` 字节不变。

自动替换规则固定为：

1. 手动正文可以显式替换任何正文；自动抓取永不覆盖手动正文。
2. 没有有效旧正文时，只接受正文可用且质量状态至少为 `usable_partial` 的首个候选；failed 非空错误页仍拒绝。
3. 有旧正文时，候选必须非占位、状态不更差、来源权威不更低，且规范化正文长度不少于旧正文的 60%。
4. 图片或 HTML 数量不能抵消正文质量下降；缺失的可选旧产物在校验有效时复制进新快照，不能因本轮缺失而静默删除。
5. 被拒绝时保留活动目录，返回 `partial` 和稳定原因码 `candidate_lower_quality`。

来源权威顺序为：人工补录 > 官方 raw/API > 站点专用抓取器 > 通用 Readability > 元数据/占位。60% 是 v2.2 的保守初始门槛，集中定义并由固定质量向量测试，不包装成普适内容质量判断。

scraper 结果新增显式 `authority` 枚举，禁止从自由文本 `source` 猜等级。没有 manifest 的旧正文使用只可由人工替换的 `legacy_unknown` 保护级别。`candidate_lower_quality` 和 `legacy_content_conflict` 均返回 `retryable: false`，队列不得把安全拒绝升级为四次重试或 `manual_required`。低质量拒绝只把 reasonCode 写入备份排除的原子运行 sidecar `.linggan/archive-attempts.json`，不能改活动 archive 中受 manifest 保护的 metadata；canonical 迁移冲突则随新快照写入 `metadata.json.migrationWarnings`。

每个新归档包含 `manifest.json`，记录相对路径、字节数和 SHA-256。提交使用 `archive → rollback`、`staging → archive`、复读 manifest、完成或逆序恢复的目录事务；启动时处理残留事务标记。

为保证常规降级到 2.1 后不会被旧版原地抓取覆盖，2.2 每次接受候选时还要把同一已验证快照按真实字节复制（禁止 hardlink）到 `entries/<uid>/protected-generations/<snapshotId>/archive/**`，并在活动 archive 验证成功后原子更新 `protected-generations/current.json`。`current.json` 必填 `{version:1,uid,snapshotId,manifestSha256,createdAt}`；目录 UID、snapshotId 与 manifest 必须一致。保护代在活动 archive 交换前完成 fsync、复读和 manifest 验证，归档事务 marker 记录 `protectedSnapshotId/protectedManifestHash`；崩溃恢复能从已验证保护代完成提交或恢复旧态。每个 UID 的 current 保护代绝不按时间自动删除，v2.2 不提供删除 current 的 API；未来若提供，只能在用户选择并通过本机完整性验证的完整 v2 备份明确包含同 snapshotId/hash 后二次确认。新保护代与活动 archive 都验证成功后，较旧保护代可保留至多一份用于事务回退，再安全清理。首次迁移也要为每个有效 canonical archive 建立保护代。

正文质量只比较去掉应用生成头部、合并空白后的正文字符数。状态等级固定为 `usable_clean > usable_partial > unusable`；缺少可选 HTML/图片属于 `usable_partial`，占位、空正文、`failed` 和 `manual_required` 属于 `unusable`。归档 manifest v1 的字段结构如下；hash 是文档占位，完整可验夹具以 `lib/fixtures/v2.2/` 为准，精确 schema 见 14.5：

```json
{
  "version": 1,
  "snapshotId": "123e4567-e89b-42d3-a456-426614174000",
  "createdAt": "2026-08-14T12:00:00.000Z",
  "quality": {
    "manual": false,
    "authority": "site_scraper",
    "state": "usable_clean",
    "normalizedChars": 18420
  },
  "files": [
    {"path": "content.md", "bytes": 18420, "sha256": "<64 lowercase hex>", "provenance": "fresh"},
    {"path": "metadata.json", "bytes": 420, "sha256": "<64 lowercase hex>", "provenance": "fresh"}
  ]
}
```

`files` 不包含 manifest 自身；活动目录除 `manifest.json` 外不得存在清单外文件。

### D8. 完整性只证明本地文件状态

`lib/archive-integrity.js` 只执行 `lstat`、读取和 hash：

- `not_archived`：没有活动归档；
- `unverified`：旧归档没有 manifest，不能称为损坏；
- `unchecked`：有 manifest，但没有与当前 `snapshotId` 匹配的扫描结果；
- `healthy`：清单文件存在、可读、大小和 SHA-256 一致；
- `damaged`：细分 `missing`、`missing_manifest`、`unreadable`、`checksum_mismatch`、`invalid_manifest`、`unexpected_file`、`unsupported_file_type`。

扫描不访问来源站点、不修改归档 mtime，也不声称内容最新。旧归档不自动建立“可信”基线。可重建的扫描缓存以 `uid + snapshotId` 为键，不进入用户备份；归档提交、导入和回滚都原子失效旧键，删除/损坏缓存后诚实回到 `unchecked`。

## 6. API 合同

### 备份

- `GET /api/backup`：默认导出 v2。
- `POST /api/backup/prepare`：上传并验证、初次预检、暂存，返回 `transactionId`、范围、字节数、警告和预计空间；活动数据不变，也不跨请求持有维护锁。
- `POST /api/backup/commit`：重新预检后锁定并提交已准备事务，返回 `committed`、`rolledBack` 和恢复摘要。
- `POST /api/backup/cancel`：取消未提交事务并清理 staging。
- `POST /api/backup/import`：保留一版兼容，内部仍走同一事务协调器并自动回滚。

v2 清单采用排序后的扁平文件表。以下 JSON 只展示字段形状，省略其余文件，不能直接作为导入夹具：

```json
{
  "format": "linggan-backup",
  "version": 2,
  "createdAt": "2026-08-14T08:00:00.000Z",
  "source": {"appVersion": "2.2.0", "dataVersion": 2},
  "manifest": {
    "algorithm": "sha256",
    "fileCount": 12,
    "totalBytes": 123456,
    "scopes": ["data", "entries", "brainstorms", "trash", "orphans"]
  },
  "files": [{
    "path": "entries/<uid>/notes.md",
    "encoding": "base64",
    "bytes": 123,
    "sha256": "<64 lowercase hex>",
    "data": "..."
  }]
}
```

`encoding` 在 v2 中只能是 `base64`，SHA-256 覆盖 Base64 严格解码后、实际将写入磁盘的原始字节。`fileCount` 等于 `files.length`，`totalBytes` 是所有解码字节之和；记录按规范路径 UTF-8 字节升序排列。manifest 自身不计入文件数和总量，未来版本一律以 `unsupported_version` 拒绝且零写入。

路径统一使用 `/`，每段先转 Unicode NFC；每段 1–120 个 Unicode 标量、完整相对路径最多 1024 个 UTF-8 字节。拒绝空段、`.`、`..`、绝对路径、反斜杠、控制字符、`< > : " | ? *`、尾随点/空格，以及不区分大小写且忽略扩展名后的 `CON/PRN/AUX/NUL/COM1…9/LPT1…9`。按 `NFC + lowercase` 检查碰撞；stage 写后重新枚举并验证真实路径，不跟随符号链接或 NTFS reparse point。Base64 必须规范编码，manifest 与实际文件集合完全一致。

### 待处理与归档

- `GET /api/attention`：返回固定策略、计数、条目和原因码；读取失败不影响 `/api/data`。
- `POST /api/lifecycle`：设置下次回顾、清除计划或标记已回顾；只允许当前条目与白名单动作。
- `GET /api/archive/statuses`：一次返回当前 `DATA.md` 条目的轻量状态；保留单项接口一版兼容期。
- `POST /api/archive/integrity/check`：每批最多 200 个 ID，只做本地扫描。

状态批量读取不计算 hash、不联网；没有任务且没有活动归档时返回 `not_archived`，不再伪装成 `queued`。前端失败时显示“状态暂不可用”，不伪造成功状态。

最小响应合同为：

```json
{
  "ok": true,
  "generatedAt": "2026-08-14T08:00:00.000Z",
  "policy": {"unresearchedDays": 7, "stalledDays": 14, "reviewDays": 30},
  "counts": {
    "items": 8,
    "byReason": {"archive_blocked": 1, "review_due": 2, "open_action": 1, "stalled": 1, "unresearched": 3, "lifecycle_missing": 2},
    "warnings": 0
  },
  "warnings": [],
  "items": [{
    "id": "1.1",
    "uid": "11111111-1111-4111-8111-111111111111",
    "title": "示例",
    "reasons": [{"code": "review_due", "priority": 2, "dueAt": "2026-08-13T08:00:00.000Z"}],
    "lifecycle": {"createdAt": null, "lastStudiedAt": null, "nextReviewAt": "2026-08-13T08:00:00.000Z"},
    "warnings": []
  }]
}
```

`POST /api/lifecycle` 的动作白名单为 `set_review`、`clear_review`、`mark_reviewed`、`repair_lifecycle`；服务器生成“当前时间”，客户端不能直接伪造 `lastStudiedAt`。批量状态和完整性响应的精确字段以 14.6 为准；状态逐 ID 返回 `not_archived`、`unverified`、`unchecked`、`healthy` 或 `damaged` 及稳定原因码。

备份事务核心错误码包含 `invalid_bundle`、`checksum_mismatch`、`insufficient_space`、`transaction_expired`、`state_changed`、`commit_failed_rolled_back` 和 `manual_recovery_required`；完整稳定码全集与 HTTP 映射以 14.6 为唯一规范。界面文案可以本地化，但代码和测试只断言稳定错误码。

## 9. 故障与回滚矩阵

| 故障 | 用户可见结果 | 系统动作 |
| --- | --- | --- |
| 格式、路径、大小或 checksum 非法 | “预检未通过”，列出稳定原因码 | 不创建活动文件，不进入维护模式。 |
| 磁盘空间不足 | 显示需要、可用和安全余量 | 不创建快照，不修改活动数据。 |
| staging 写入或复读失败 | “准备失败，当前数据未改变” | 清理或隔离 staging；prepare 不持有跨请求维护锁。 |
| 回滚快照不完整 | “无法安全开始恢复” | 中止提交，保留当前活动数据。 |
| 任一 swap 或提交后校验失败 | “恢复未完成，原数据已自动恢复” | 按 journal 逆序恢复；仅验证成功后返回 `rolledBack: true`。 |
| 自动回滚也失败 | 阻断后续写入并显示恢复路径 | 保留 old、stage 和 journal，启动时再次恢复；不得继续报告服务健康。 |
| 归档候选较差 | “保留最近有效正文”及原因 | 删除/隔离候选，活动归档不变。 |
| 完整性损坏 | 显示损坏文件和本地原因 | 不自动联网、不自动覆盖；允许从完整备份或显式重抓恢复。 |
| 待处理 API 失败 | “待处理信息暂不可用” | 主看板与本地数据继续可读写。 |

## 11. 风险与控制

| 风险 | 控制与退出条件 |
| --- | --- |
| Windows 杀毒软件或索引器短时占用目录 | rename 只做有限、带退避的重试；超过期限立即回滚，不用递归删除绕过占用。 |
| 50 MiB 无法覆盖大规模资料 | 导出前准确显示总量和最大文件，拒绝残缺包并给出数据目录复制指引；不在本版仓促引入 ZIP 依赖。 |
| 60% 正文门槛误拒绝更短但更好的内容 | 拒绝只会保留旧正文，不造成损失；人工补录可显式替换，质量原因码用于后续调参。 |
| 最近有效保护代增加本地占用 | 每 UID 只强制保留 current，上一代仅跨事务短期存在；导出预览计入真实字节，v2.2 不提供删除 current 的入口。 |
| 历史条目没有可信时间导致待处理噪声 | 单列低优先级“日期未知”，不计算逾期；用户首次真实操作后再建立时间。 |
| `board.js` 继续增大 | 本版 UI 只增加薄入口和渲染适配，规则放在 `lib/attention.js`；完整前端拆分留到 2.3。 |
| CI 打包时间或联网波动 | 固定夹具作为阻断门禁；Node 运行时下载使用校验与缓存，真实外站冒烟单独记录。 |

## 12. CI 与发布门禁

scraper 测试拆成固定夹具和真实联网两组；只有固定夹具进入稳定 CI，联网冒烟定时或人工记录，不能把“优雅失败”当成成功率证明。

合并和发布至少执行：

```text
npm run check
npm run coverage
npm run test:scrapers:fixtures
npm run test:e2e
```

1. 可先发布 `v2.2.0-rc.1` 验证体验，但稳定版必须从最终的 2.2.0 候选 commit 重新走受控候选 workflow。

3. 首次启动先创建并验证升级前快照，再启用任何生命周期、正文或队列迁移。
4. `DATA.md` 保持版本 2，2.1 可忽略新增注释；常规降级只替换程序，不回退数据。
5. v2 完整备份不能由 2.1 导入；升级快照只用于数据已损坏或迁移不兼容的显式灾难恢复，恢复前尽可能先导出当前 2.2 救援包并二次确认，绝不随程序降级自动覆盖新数据。

## 14. 冻结的实现合同

本节是 `BASE-01` 的规范来源。实现若需要改变这里的字段、状态或边界，必须先修改计划、夹具和契约测试，不能在代码中另设隐式规则。

### 14.1 备份格式与数据范围

#### v1 兼容输入

v1 顶层必须包含 `format: "linggan-backup"`、`version: 1`、字符串 `data` 和数组 `entries`；`createdAt` 可缺失或为字符串，其他顶层未知元数据忽略。每个 entry 只能有 `uid,id,files`：`uid` 是迁移后 `DATA.md` 中存在的非空字符串，`id` 可缺失或为字符串，`files` 是数组，同一 UID 不得重复。每个 file record 必须且只能是当前 2.1 exporter 的实际结构 `{name,encoding,data}`，三者都是字符串；`name` 是下表中的规范相对路径，`encoding` 必须与该路径对应的下表值完全相同，`data` 在 utf8 时是无孤立代理项的文本、在 base64 时是第 14.1 节规定的规范 Base64。utf8 以无 BOM 的 UTF-8 字节计入容量，base64 以严格解码后的字节计入容量；v1 没有 bytes/hash 字段，适配器必须自行计算且不能信任 JSON 字符数。同一 entry 内按 NFC 后的 UTF-8 路径和 Windows 大小写折叠两种键检查重复，任一冲突拒绝；entry 和 file record 的未知字段均以 `invalid_bundle` 拒绝。历史白名单和编码固定为：

| 路径 | 编码 |
| --- | --- |
| `notes.md`、`content.md` | `utf8` |
| `screenshots/<安全文件名>.png|jpg|jpeg` | `base64` |
| `archive/metadata.json`、`archive/content.md` | `utf8` |
| `archive/raw.html.gz` | `base64` |
| `archive/images/<安全文件名>.png|jpg|jpeg|gif|webp|svg|bin` | `base64` |

结构、UID、重复路径、编码、Base64 或路径非法时整包以 `invalid_bundle` 拒绝且零写入。图片 magic、JSON 或 gzip 内容无效但字节本身处于容量限制内时，不放入活动归档，而是按本节统一 orphan 容器以 `corrupt_v1_artifact` 原因原样保存并产生预览警告；gzip 只做有输出上限的验证。历史 SVG 和 BIN 也始终按 opaque 字节进入该隔离范围，不在活动界面渲染。这样既不执行不可信内容，也不静默丢弃旧包中的用户字节。

v1 的写入语义是“替换 DATA + 覆盖显式列出的白名单文件”：同 UID 未列文件保留，不在新 DATA 中的当前 UID 目录整体移至 `orphans/<transactionId>/removed-entries/`；brainstorms、trash 和既有 orphans 保留。适配器在同一次 stage 中立即 canonicalize 正文，绝不把根级 `content.md` 写进活动结构：仅有根正文时转成新的 `archive/content.md` 与 `legacy_unknown` manifest；根正文和 archive 正文相同则去重；两者不同则 archive 版为活动正文、根版进入 `attachments/legacy-content-<hash>.md`。v1 列出任何 archive 文件时，都以“导入记录覆盖 + 未列旧文件保留”的 union 重新验证并生成完整新 manifest，不能沿用旧 manifest。所有保留、转换与隔离内容都在 commit 独占 lease 内从最新活动态 rebase，不使用 prepare 时的陈旧副本。

v1 适配结果也必须满足 active/current 不变量：只要 union 产生有效活动 archive，就在同一次 stage 中生成与之逐字节相同的新 current 保护代；导入前 current 可作为唯一 previous 保护代保留。若导入后没有活动 archive，则不得留下 current。该规则意味着显式 v1 导入可以更换 current，但被替换的上一份保护代和事务 old 都先保全，提交失败不能删除它们。

v1 兼容仍受 80 MiB HTTP body、50 MiB 解码总量、5000 文件和第 14.1 节单文件上限约束；历史导出若利用旧版校验漏洞超过这些安全边界，以 `bundle_too_large` 拒绝并提示复制数据目录，不能为“兼容”而无界读取。

#### v2 规范形式

v2 必填字段就是第 6 节示例中的 `format:'linggan-backup'`、`version:2`、规范 UTC 毫秒格式 `createdAt`、非空 SemVer 字符串 `source.appVersion`、`source.dataVersion:2`、`manifest.algorithm:'sha256'`、`fileCount`、`totalBytes`、`scopes` 和 `files`；每个 file 必填 `path`、`encoding:'base64'`、非负安全整数 `bytes`、64 位小写十六进制 `sha256` 与字符串 `data`，`raw.html.gz` 还必须有非负安全整数 `uncompressedBytes`，且等于有界解压实际字节数。顶层、source、manifest 的未知元数据在校验和 canonical hash 前丢弃，file record 出现未知字段则拒绝，防止隐藏 payload。v2 只接受完整快照，`manifest.scopes` 必须严格等于按此顺序排列的 `['data','entries','brainstorms','trash','orphans']`，本版不接受部分 scope。虚拟路径到活动目标的映射固定为：

| 虚拟路径 | 活动目标 |
| --- | --- |
| `DATA.md` | `README_FILE` 指向的文件，且包内必须恰好一份 |
| `entries/**` | `ENTRIES_DIR/**` |
| `brainstorms/**` | `BRAINSTORM_DIR/**` |
| `trash/**` | `TRASH_DIR/**` |
| `orphans/**` | `.linggan/recovered-orphans/**`（实现为可配置的 `RECOVERED_ORPHANS_DIR`） |

成功执行普通 v2 导入后，五个声明范围都与包内集合完全一致：包中缺失即表示新快照中不存在，但被替换的完整旧根仍保留在事务 old 快照中。第 14.2 节的 restore_backup recovery import 是唯一例外：它可以把当前安装中仅存于运行 sidecar 的人工正文，以预览中明确列出的 rescue overlay 写入新 stage；overlay 必须由 descriptor 的 `rescueOverlayHash` 单独证明，不能借此合并其他本地文件。restore_upgrade_snapshot 不做 overlay，而把当前运行字节保存在逐 target rescue 中并原样安装完整升级前快照。v1 转换新增的隔离内容放在新 stage 的 `orphans/<transactionId>/**`，同时在锁内 rebase 当前已有 recovered-orphans。空目录不序列化，应用按需重建。默认 `.linggan` 根是 `path.dirname(README_FILE)/.linggan`；显式的 `BRAINSTORM_DIR`、`TRASH_DIR`、`ENTRIES_DIR` 或 `RECOVERED_ORPHANS_DIR` 可位于其他卷，且各自独立成为事务目标。

启动时对所有目标和控制目录做 topology 校验：解析绝对路径、现存部分的 realpath 及 Windows 不区分大小写形式；`README_FILE` 必须是普通文件目标，其余必须是目录目标；任意两个 live 目标不得相等、互为祖先/后代。任一 live 目标与 `.linggan/import-transactions`、upgrade snapshots、queue、idempotency 等控制文件/目录也不得相等或互为祖先/后代；文件目标同时禁止位于控制目录内。stage、old、marker 及其父目录不得落入任何其他 live 或控制根。根本身是 symlink、junction 或 reparse point 时拒绝启动并返回 `invalid_storage_topology`，在通过前零写入。

同一进程的 mutation lease 之外，还必须有跨进程 instance lock。锁资源集合是全部 canonical live 目标加 canonical `CONTROL_DIR`；这样不同 `README_FILE` 只要共享 `.linggan` 控制根也必然争用同一把锁。路径即使尚不存在也先按绝对、NFC、Windows 大小写规则规范化。锁锚点不能随目录出现而漂移：CONTROL_DIR 锁固定放在 `path.dirname(CONTROL_DIR)`，其余资源锁固定放在 `path.dirname(resource)`；缺失父目录只能由 Node 在记录 preexisting inventory、取得对应 volume mutex 后创建为空 scaffolding。锁目录永远不放入 resource 自身、stage/old 或任何会被 swap 的根，resource 已存在时也绝不从 resource 本身起步。

为覆盖不同配置、不同 OS 用户把 live roots 设成祖先/后代的情况，取得细粒度资源锁前还要按卷取得跨用户、由内核持有的保守 volume mutex，并持有到进程退出。同一卷上任何两个灵感工作台实例互斥，即使它们的资源路径表面不重叠；这是 v2.2 为数据安全接受的限制。volumeId 在 POSIX 使用根目录的 bigint `stat.dev`，Windows 使用卷序列号与规范卷 GUID 的组合，并以同卷盘符/挂载别名夹具验证一致；无法得到稳定 ID 时拒绝启动，不退化为路径字符串。

所有目标卷按 volumeId 排序取得 kernel mutex，任一失败即释放本轮已取 mutex。Windows 使用 `Global\\LingganWorkbench.Volume.v2.<volumeIdSha256>` named mutex，固定 ACL 允许本机 authenticated users 同步/取得但不允许任意改写描述符；POSIX 使用经审计的原生 `flock(LOCK_EX|LOCK_NB)` helper，锁住 root 所有、01777、非 symlink 的 `/var/tmp` 下持久普通文件 `linggan-workbench-volume-v2-<volumeIdSha256>.lock`，文件以 `O_CREAT|O_NOFOLLOW` 打开、创建者立即固定 0666、复核 fd/path 的 device+inode，且应用永不 unlink/rename。kernel mutex/文件描述符随进程崩溃自动释放，不存在 stale 删除；平台 helper、ACL 或安全 registry 不可用时拒绝启动。源码、CLI 和 Windows 单 EXE 使用同一 N-API ABI helper并同时验证 Node 22/24；单 EXE 只把构建时固定 SHA-256 的对应 arch `.node` 资产原子解出到版本+arch+hash 私有缓存后加载，hash 不符即拒绝。UNC、SMB、NFS 或其他可能被多主机同时挂载的目标在 v2.2 直接以 `invalid_storage_topology` 拒绝，不能把本机 kernel mutex 宣称为分布式锁。这样不同 CONTROL_DIR、不同用户下的 `X/common` 与 `X/common/subdir` 也不能并发，live→old 不会搬走 volume mutex。固定双进程夹具覆盖两个 OS 用户、相同路径、祖先/后代路径、同卷不相交路径、盘符/挂载别名、helper 崩溃和 swap 中 contender；不同卷且资源完全独立才允许并行。

获取前先做只读 preexisting inventory。取得全部 volume mutex 后，先创建并复读缺失的 CONTROL lock-parent 空 scaffolding，再在该固定锚点取得 CONTROL_DIR 锁；在它保护下只允许为其他锁创建缺失的空父目录 scaffolding，每段都必须不是 symlink、junction 或 reparse point，尚未创建任何 live 目标或用户文件。接着按资源规范路径排序在这些固定父目录取其余锁。全部锁取得后再次扫描 inventory；除本次 nonce 的 lock dirs 与刚建的空 scaffolding 外必须与 preexisting inventory 一致，否则释放锁并以 `state_changed` 重试，fresh 判定始终使用首次 inventory。即使不同 CONTROL_DIR 的进程共享同一外置目标，它们也会在 coarse volume mutex 下建立同一个固定父目录，再竞争同一最终锁名。

每把资源锁的最终名是 `.linggan-owner-<规范路径sha256前16位>.lock`；只有已持有该资源所在卷 kernel mutex 的进程才可创建、检查或清理它。唯一 claim 原语是在固定父目录直接执行原子 `mkdir(final)`。`EEXIST` 一律表示未取得锁，调用方不得写入或用 rename 覆盖该目录；不能用“先 exists 再 rename”的 TOCTOU 方案。mkdir 成功后才在已独占目录内以临时文件、fsync、rename、复读写 `owner.json`；owner 必填随机 128 bit nonce、PID、进程启动时间、全部资源的 descriptor hash、createdAt 和每 10 秒原子更新的 heartbeat。进程只有在 owner 复读成功后才可写用户数据；此前崩溃会留下保守的 ownerless lock，而不是让第二实例进入。任一锁失败就按 nonce 复核并释放本次已取资源锁和 kernel mutex，再返回 `data_in_use`。

有效 owner 只有在 PID 不存在或进程启动时间不匹配、且 heartbeat 超过 2 分钟时才可判 stale。final 缺少/损坏 owner 时，必须对目录 identity、完整内容 hash 和 mtime 做两次相隔至少 2 分钟的观察且完全不变，才能形成 `ownerless_stale` 证据；仍需用户提交绑定该证据的确认 token，无法证明时绝不抢锁。条件清理前必须先独占全部目标卷 kernel mutex，再重新读取 token 绑定的目录 identity、owner bytes hash、内容 hash、mtime 和 stale 证据；完全相同才把 final 原子 rename 到带该证据 hash 和随机 nonce 的 quarantine 路径并 fsync 父目录，之后只删除该唯一 quarantine，绝不再按 final 路径删除。mutex 持有期间其他合规实例既不能创建新 final，也不能清理；因此不会把观察后的新 owner 当旧锁删除。随后仍须在 mutex 保护下重新以 mkdir 取得全部资源锁，不能把清理视为已经持锁。未取得 kernel mutex 的 server 只能启动不读取用户数据的 lock-conflict shell，提供 health、锁状态和 `POST /api/recovery/clear-stale-lock`。server 生命周期内持有全部 mutex/资源锁，优雅关闭也仅在 owner nonce/descriptor 仍匹配时释放。CLI 检测活动 server 时只提示改走 recovery API；server 停止后，破坏性 CLI 只能以单进程交互会话取得同一 helper/锁、读取 status、在内存生成状态绑定 challenge/token并立即执行，进程退出即失效，无 `--force`、静态 hash 或跨进程 token 绕过。双 server、server+CLI、两个 OS 用户、不同 README 共享控制根、缺失目标父目录、A 持锁期间目录出现而 B 后启动、现存 resource 执行 live→old 期间 contender 始终被 kernel mutex 阻断、mkdir 后/owner 写前崩溃、POSIX 空 final、两个 cleaner、PID 复用和 stale-lock 都有双进程测试；每个竞态最多一个进程进入用户数据区。

所有 v2 payload 都是 RFC 4648 标准字母表、无空白、正确 padding 的规范 Base64；长度必须为 4 的倍数，严格解码后重新编码要与输入逐字节相同。之后再计算 `bytes` 与小写十六进制 SHA-256。`fileCount === files.length`，`totalBytes === sum(files[].bytes)`；记录按 NFC 规范路径的 UTF-8 字节无符号字典序排序。manifest 自身不进入 `files`、`fileCount` 或 `totalBytes`。未来 `version` 以 `unsupported_version` 零写入拒绝。HTTP 层无论是否有 `Content-Length` 都在读取流时执行 80 MiB 原始 body 上限，超限后立即停止读取，不先解析 JSON。

canonical bundle JSON 的字段顺序固定为：顶层 `format,version,createdAt,source,manifest,files`；source 为 `appVersion,dataVersion`；manifest 为 `algorithm,fileCount,totalBytes,scopes`；file 为 `path,encoding,bytes,sha256,uncompressedBytes(仅 gzip),data`。对象无额外空白，数组使用上述固定顺序，UTF-8 不做 ASCII 转义；bundle/request content hash 都是这段字节的 SHA-256。

容量分类闭合为：整个解码包 50 MiB、HTTP JSON 80 MiB、5000 个 file record；截图单文件 5 MiB，活动归档 PNG/JPEG/GIF/WebP 图片 10 MiB，raw gzip 压缩和解压后都各 20 MiB，其他任意普通文件（含 DATA、notes、draft、brainstorm、trash、attachment、orphan）单文件 20 MiB。所有上限均以 `1024 * 1024` 计，等于允许、超 1 字节拒绝。

`DATA.md`、notes、brainstorm、trash Markdown 与已知 JSON 必须用 fatal UTF-8 解码；DATA 必须是 data-version 2、UID 唯一且每个 `entries/<uid>/` 都能在其中找到。entries scope 只允许 canonical notes/screenshots/archive、`attachments/**`、严格配对的 `drafts/manual-<64位小写sha>.md` 与同 basename `.json`，以及至多两份 `protected-generations/<UUID>/archive/**` 和唯一 `protected-generations/current.json`。保护代只能包含按 14.5 archive schema 自洽的完整快照；有有效 v2 活动 archive 时必须有 current，current 的 uid/snapshotId/manifestSha256 及保护代全部文件字节必须与活动 archive 完全相同；没有活动 archive 时禁止 current。另一份保护代只能是同 UID 的前一已验证代。active/current 任一缺失、错配或同路径字节不同都会使外来 v2 整包以 `invalid_bundle`、details reason `archive_generation_mismatch` 零写入拒绝；导入、归档 commit 与回滚必须在同一事务中维护该不变量。草稿 JSON 必填 `{version:1,uid,sha256,createdAt,origin}`，createdAt 为规范 UTC 或仅在崩溃恢复时为 null，origin 为 `manual|legacy_recovery`；目录 UID、文件名、正文 hash 和 JSON uid/hash 必须一致。启动发现“正文存在、JSON 缺失”时可用已知目录 UID/hash 补 `createdAt:null,origin:'legacy_recovery'`，发现仅 JSON、hash 不匹配或特殊文件则把所有现存字节映射到 reason `orphaned_manual_draft` 并预警，绝不覆盖。已知 JSON 要通过 schema，活动图片只允许 PNG/JPEG/GIF/WebP 并通过 magic，raw gzip 要通过有界解压，带 manifest 的 archive 必须集合完全一致。任一语义不合法的外来 v2 包整包拒绝。导出本机已经损坏的活动 archive 时不伪造健康包：把该 archive 的全部普通字节虚拟映射到 orphan 容器，从 entries scope 排除它并显示警告；特殊文件仍使导出失败。

上句“从 entries scope 排除”只指损坏 live 字节：若 current 保护代完整有效，导出器必须把它的 archive 字节虚拟提升到 active 路径并与 current 成对输出，同时把损坏 live 字节映射到 orphan；若 current 也缺失或损坏，则 active 与全部 protected/current 一并从 entries 排除，其普通字节全部进入 orphan。两种输出都必须再次通过同版 v2 validator。固定往返夹具删除 active manifest 但保留健康 current，断言导出包可重新导入并恢复保护正文。

任何“不属于活动 scope 白名单但必须保全”的普通文件都使用同一确定性 orphan 容器：`orphans/unclassified/<来源scope>/<原相对路径UTF8的SHA-256>/<内容SHA-256>/payload.bin` 保存原字节，且必须与同目录 `metadata.json` 成对存在。sourceScope 只能是 `data|entries|brainstorms|trash|orphans|runtime`；sourcePath 只能是 NFC、正斜杠、非绝对的规范虚拟路径，绝不写宿主机绝对路径。metadata 必填且按此字段顺序 canonical JSON：`{version:1,sourceScope,sourcePath,sourcePathSha256,contentSha256,originalExtension,bytes,reasons,firstSeenAt,lastSeenAt}`。hash 为小写 SHA-256，bytes 为 payload 实际字节，originalExtension 为含点的小写扩展或空字符串；reasons 是去重字典序数组，只允许 `unclassified|damaged_archive|corrupt_v1_artifact|orphaned_manual_draft|removed_entry|downgrade_candidate|failed_new_generation|invalid_protected_generation`。firstSeenAt/lastSeenAt 是规范 UTC 且 first 不晚于 last；重复发现同 path+content 时保留最早 first、以服务器当前时间推进 last 并合并 reasons，导入已有记录时保留包内时间，固定时钟下结果确定。未知字段、单边文件、目录 hash/字段/hash/bytes 不一致都使外来 v2 整包拒绝。完整路径 hash 避免文件名清洗碰撞，内容 hash 让同路径不同版本并存；两个 record 同样计入 5000 文件与容量上限。

路径逐段执行：转 NFC；每段 1–120 个 Unicode 标量；完整相对路径不超过 1024 个 UTF-8 字节。拒绝空段、`.`、`..`、绝对路径、反斜杠、NUL/控制字符、Windows 禁止字符 `< > : " | ? *`、尾随点或空格，以及去掉扩展名后为 `CON`、`PRN`、`AUX`、`NUL`、`COM1`–`COM9`、`LPT1`–`LPT9` 的设备名。以 `NFC + Unicode lowercase` 后的完整路径判碰撞。枚举、staging 和校验都用 `lstat`，拒绝符号链接、junction、reparse point、设备和非普通文件。

当前数据指纹覆盖五个用户 scope 及 v1 commit 需要保留的范围。每个普通文件生成 `规范虚拟路径 + NUL + 十进制字节数 + NUL + 小写 SHA-256 + LF`，按路径比较器排序后再对整串做 SHA-256；目录本身和 mtime 不参与。每个文件读取前后都用同一 fd `fstat` 核对 identity、大小和高精度 mtime，完整 inventory 连续扫描两次必须相同，否则返回 `state_changed`。prepare 保存稳定值，commit 在独占 lease 内重新计算；内容相同长度但改了 1 字节也必须被发现。

### 14.2 事务、维护锁与崩溃恢复

中央 journal 位于 `.linggan/import-transactions/<id>/transaction.json`，最低 schema 如下；尖括号值仅表示字段类型，真正夹具使用合法 UUID、路径和 hash：

```json
{
  "version": 1,
  "id": "<uuid>",
  "requestId": "<uuid>",
  "kind": "import-v2",
  "createdAt": "<UTC ISO>",
  "expiresAt": "<UTC ISO>",
  "state": "prepared",
  "liveFingerprint": "<sha256>",
  "bundleSha256": "<sha256>",
  "targets": [{
    "scope": "entries",
    "live": "<absolute path>",
    "stage": "<sibling absolute path>",
    "old": "<sibling absolute path>",
    "hadLive": null,
    "oldManifestSha256": null,
    "stageManifestSha256": "<sha256>",
    "markerSha256": "<sha256>",
    "state": "stage_ready"
  }],
  "terminalResult": null
}
```

普通导入的全局状态只能按 `preparing → prepared → committing → committed → completed`、`preparing → expired`、`prepared → cancelled|expired`，或由 `committing|committed → rolling_back → rolled_back → completed` 演进；自动收敛失败进入 `manual_recovery`，之后普通导入只允许 `manual_recovery → rolling_back → rolled_back → completed`。独立 recovery import 使用第 14.2 节自己的 journal、active pointer 与终态，不能借改写原 journal 猜测进度。普通 journal 的 `terminalResult` 只区分该普通事务自身的最终提交或回滚；外部备份恢复只写独立 recovery journal/root marker 的 terminalResult 与 supersedesOriginal，原 journal 始终只读。提交目标状态按 `stage_ready → old_ready → live_ready → verified`，回滚目标状态按 `rollback_ready → old_restored → old_verified` 演进。`completed`、`cancelled`、`expired` 是终态，`manual_recovery` 是阻断态；一次仅允许一个其他非终态导入事务。UUID `requestId` 与 bundle hash 共同提供幂等，复用同一 ID 但内容不同返回 `idempotency_conflict`。bundle hash 是把已验证、已排序且采用固定字段顺序的内部 bundle 表示序列化为无额外空白 UTF-8 JSON 后计算的 SHA-256；v1 先转换为该表示。

journal、目标 manifest 和 app marker 均采用同目录临时文件、`fsync` 文件、rename、复读校验；支持目录 `fsync` 的平台还要同步父目录，Windows 至少重新打开目标并复核长度与 hash。文件系统动作完成并持久化后才能推进对应状态。rename 遇 `EPERM`、`EACCES` 或 `EBUSY` 时只在 50/100/200/400/800 ms 后各重试一次（连首次共 6 次），其他错误立即失败；不得用递归删除绕过锁。prepared 时 `hadLive` 与 `oldManifestSha256` 允许为 null；commit 必须先在锁内为全部目标计算并持久化 `hadLive`、old manifest 和 marker，全部成功后才把全局状态写为 `committing`，再开始第一处 rename。成功提交后的 old 不在响应前删除，old、对应 marker 和可恢复 journal 作为一组按第 5 节的 7 天/最多 2 组策略清理。

每个目标在 live 的父目录使用唯一 `<name>.import-<id>.txn/` sidecar 目录，内含 `descriptor.json`、`stage.manifest.json`、`old.manifest.json` 和 `marker.json`；目录名和四个文件都不得被其他事务复用或覆盖。相同 descriptor 副本写到每个卷，必填 `version,id,kind,bundleSha256,targets`；targets 是按 scope 排序的完整预期集合，每项含 `scope,live,rootType,stage,old`。目标 manifest 是按 rootType 区分的固定联合：目录目标为 `{version,transactionId,scope,rootType:'directory',existed,fileCount,totalBytes,files}`，files 使用相对目标目录的规范非空路径、bytes、sha256 并按 UTF-8 字节排序；文件目标为 `{version,transactionId,scope,rootType:'file',existed,bytes,sha256}`，不含 files/fileCount/totalBytes，也不伪造空路径、`.` 或 basename。任一目标 existed:false 时目录使用 `fileCount:0,totalBytes:0,files:[]`，文件使用 `bytes:0,sha256:null`；existed:true 时所有计数/hash 必须与复读字节一致。字段按上述顺序编码为无额外空白 canonical JSON，其 SHA-256 统一用于 ordinary/recovery-import 的 live/stage/newStage/old/rescue/failedNew 判据，sidecar 自己不入清单。marker 必填 `version,transactionId,descriptorSha256,scope,live,stage,old,hadLive,stageManifestSha256,oldManifestSha256,state,updatedAt`，状态与 journal 目标状态相同。descriptor hash 覆盖不可变 descriptor 全文，不会因状态推进改变。每次动作先写/验证 descriptor 与相应 manifest，再写 marker，最后把 marker hash 和状态写进中央 journal；恢复允许 journal 落后一格，但所有 descriptor 副本、transactionId、scope 与 manifest hashes 必须一致，descriptor 中任一预期 target/marker 缺失都进入 `manual_recovery`，不能要求旧 marker 匹配可变 journal 整体 hash。清理只按完整 `<id>.txn` 目录执行，下一事务开始前仍能读取保留期内任一旧事务的四个 sidecar。

恢复判据固定为：`preparing` 尚未交换活动数据，隔离残余 stage 并按 `preparing → expired` 终结；`prepared` 在 24 小时内保持可提交，超过期限只清 stage 并按 `prepared → expired` 终结；`committed` 只有在每个 live 都符合 stage manifest 时才执行队列清理并推进 `completed`，否则进入回滚；`rolled_back` 复验旧态、恢复原队列后推进 `completed`；`completed` 不再自动改动活动数据。

`committing`/`rolling_back` 按每个目标独立收敛旧态：state 为 `stage_ready` 且 live 匹配 old manifest 时直接标 `old_verified`（说明尚未交换）；live 缺失而 old 匹配时先写 `rollback_ready` 再执行 `old → live`；live 匹配 stage 且 old 匹配时先写 `rollback_ready`、把 live 隔离为 `failed-new`，再执行 `old → live`。rename 后写 `old_restored`，复验后写 `old_verified`。若崩溃发生在 old rename 后、marker 更新前，`live` 匹配 old manifest 且 `old` 缺失同样证明已经恢复，可直接补写 `old_restored/old_verified`。state 与磁盘动作可能因崩溃落后一格，因此只接受这些由 manifest 证明的组合，其他组合进入 `manual_recovery`。`hadLive:false` 的旧态是 live 不存在；任何新 live 都先隔离。只有“应该仍依赖 old 且 live 也不匹配旧态”的组合才阻断，不能把尚未第一次 rename或刚完成回滚的完整 live 误判为故障。journal 损坏时不猜新旧，使用每个目标旁已 fsync 的事务 marker 枚举候选；只有所有 scope 都能组成同一事务的完整旧代，才允许一键恢复。每个 scope 在 `old → live` 后立即崩溃都有固定故障夹具。任何路径都不得留下部分新、部分旧后继续启动。

维护协调器提供共享 mutation lease 和独占 maintenance lease。截图、笔记、回收站、头脑风暴、capture 的“保存 + 入队”、人工草稿和归档提交从第一处写到最终持久化全程持有同一个共享 token；嵌套调用沿参数传递 token。申请独占时先设置 maintenance intent、阻止新共享 lease、暂停队列调度，再等待在途 lease 最多 60 秒；超时返回 `maintenance_timeout`，不修改活动目标且不强杀 worker。导出和 prepare 的一致快照只短暂持有独占 lease；commit 持有至新态或旧态完成复验。

prepare、commit、cancel 与 24 小时清理都在事务互斥锁内检查状态。cancel 只作用于 `prepared`；`committing` 后返回冲突。重复 commit/cancel 返回已持久化的同一终态结果；过期 prepared 事务返回 `transaction_expired` 并只清理 stage。成功 commit 在写入 `committed` 后，先把旧队列、`.previous`、archive-attempts、expected index 和完整性缓存原子移入事务内 `runtime-old/` 并记录 hash，再创建空队列、按新 manifests 重建 expected index、失效缓存；导入出的人工草稿变为 `manual_pending`，不推断或启动网络任务。内存 Map 只在磁盘 reconciliation 完成后清空。崩溃后看到 committed 也执行相同步骤，再写 `completed`；若此间必须回滚，从 `runtime-old` 恢复原运行 sidecars。rolled_back 复验旧态、恢复原队列及 sidecars 后写 `completed`。`runtime-old` 与对应 old generation 同期保留，reconciliation 完成前不向 API 返回终态响应。

swap 窗口与 `manual_recovery` 模式下，仅静态恢复界面、`/api/health` 和下列 `/api/recovery/*` 可用；所有其他数据 API（包括普通 `/api/backup/prepare`）返回 503。普通维护等待期的本地写请求返回 423，真正无副作用的读取可继续；`GET /api/entry` 必须先移除自动建目录/模板的副作用。企业微信回调返回 503 与 `Retry-After: 2`；钉钉 handler 返回 `{accepted:false,retryable:true,code:'maintenance_mode'}`，向发送者回复“维护中，请稍后重新发送”，不得记录为保存成功。

恢复面固定提供：

- `GET /api/recovery/status`：列出事务、每个 live/stage/old 的本地校验结果、可验证升级快照、stale-lock 证据、每个可确认动作各自的 token 和唯一安全建议；
- `GET /api/recovery/diagnostics`：导出不含正文、路径只保留 scope 与路径 hash 的状态/manifest 诊断 JSON；
- `POST /api/recovery/retry`：重新执行上述确定性收敛规则；
- `POST /api/recovery/restore-old`：仅在所有 old 验证通过且用户提交状态页给出的短期确认 token 后执行；
- `POST /api/recovery/import/prepare`：只验证并暂存完整有效 v2 包，返回 `recoveryPrepareId/bundleHash/summary/expiresAt`，不交换活动数据也不返回 token；成功后只能由 `GET /api/recovery/status` 新发内存确认 token；
- `POST /api/recovery/import`：只接受上一步的 recoveryPrepareId 和匹配 token；先把当前 live/stage/old 全部作为 rescue generation 保全并验证，再用同一事务库安装已暂存备份，失败时恢复 rescue generation；
- `node scripts/recover.js --interactive`：只在 server 已停止时进入同一进程的恢复会话；它取得与 server 相同的锁、调用同一 status/action 服务、显示完整状态指纹并要求用户输入本轮随机 challenge，随后在该进程内生成一次性 token并立即执行。read-only 列表可脚本化，所有破坏性动作禁止 `--force`、静态 manifest hash 或跨进程 `--confirm <token>`，不让用户手工拼目录。

HTTP 模式的确认 token 只由 `GET /api/recovery/status` 在对应动作的磁盘前置条件验证成功后以 CSPRNG 生成 128 bit Base64URL 值，只存在 recovery server 内存；离线 interactive CLI 必须调用同一 token 服务并在同一进程、同一持锁会话内消费，不能导出或复用 token。recovery/import 与 upgrade snapshot restore 必须先 prepared；健康 awaiting_upgrade_choice 只有在全部 snapshot live 复验通过时才可为三种 upgrade finalize 签发 token，degraded awaiting 只可为 restore_rescue 签发；ready_for_2_1 可选择 remigrate_2_2/restore_rescue，remigrate_snapshotting/remigrating_2_2 只可选择 restore_rescue；restore-old 必须先复验全部 old 候选；clear-stale-lock 必须先完成两次 stale 观察。每个 token 精确绑定 `action + targetKey + stateFingerprint`，10 分钟过期且成功使用一次即作废，任一绑定字段或磁盘指纹变化立即失效。`restore-old` 的 targetKey 是 transactionId；其 stateFingerprint 是规范 JSON 的 SHA-256，固定覆盖 transaction state、immutable descriptor hash、全部 marker hashes，以及每个预期 scope 的 hadLive 和当前 live/stage/old 的 `present,valid,manifestHash,inventoryHash`，执行前在事务锁内完整重算，任何字节、状态或 allowedActions 变化都拒绝旧 token。`restore-upgrade-snapshot` 的 targetKey 是 recoveryPrepareId，指纹覆盖 snapshotName、snapshotManifestSha256、全部 target 的 live/newStage/rescue manifests、当前 rescue inventory 和事务状态；`finalize-upgrade-restore` 的 targetKey 是 `recoveryPrepareId:mode`，指纹另覆盖 mode、全部 snapshot live/rescue manifests、remigrate snapshot（如有）及当前 awaiting_upgrade_choice/ready_for_2_1/remigrate_snapshotting/remigrating_2_2 状态；`clear-stale-lock` 的 targetKey 是 lockDescriptorHash，指纹覆盖规范 resource path hash、owner bytes hash、目录 identity/content hash/mtime 和 PID/start-time/heartbeat stale 证据；`recovery/import` 的 targetKey 是 recoveryPrepareId，指纹覆盖 bundle hash、全部 target manifests、当前 rescue inventory hash 和事务状态。状态接口按 action/targetKey 返回独立 token，不能用一个“通用确认”替代。server 或 interactive CLI 进程结束后必须重新获取/生成。若不存在任何完整可验证代，系统保持恢复模式，只能导出诊断或通过两阶段 recovery import 安装完整 v2 备份，不宣称已恢复。此时 `/api/health` 返回 HTTP 503、`state: 'recovery_required'`。

recovery import 不是原失败事务中的一条模糊状态，而是独立、不可覆盖的事务。prepare 创建中央 `.linggan/recovery-imports/<recoveryPrepareId>/transaction.json`，并在每个目标父目录创建 `<name>.recovery-import-<id>.txn/`；相同 immutable descriptor 副本必填 `version,recoveryPrepareId,kind,originRecoveryState,originalTransactionId,bundleSha256,snapshotName,snapshotManifestSha256,rescueInventoryHash,rescueOverlayHash,targets`。kind 只能是 `restore_backup|restore_upgrade_snapshot`；originRecoveryState 只能是 `manual_recovery|data_missing|normal`。restore_backup 要求 bundleSha256 非空而两个 snapshot 字段为 null；restore_upgrade_snapshot 要求 snapshotName/hash 非空，bundleSha256 是快照映射成规范内部 target 集合后的 canonical hash。每个 descriptor target 固定 `scope,targetKind,rootType,volumeId,live,newStage,rescue,failedNew,hadLive,newExists,newManifestSha256,rescueManifestSha256`；newExists:false 时物理 newStage 必须不存在，但 newManifestSha256 必须是第 14.2 节 canonical `existed:false` target manifest 的非空 hash，new_live/new_verified 表示 live 已验证不存在。targetKind 只能 `user|runtime`，user scope 是五个备份 scope，runtime scope 只能 `queue|queue_previous|app_marker`。每个 runtime 文件都是位于自身 live 同卷、拥有独立 manifest/marker/state 的 target，不能聚合到单一 rescuePath。原失败事务的跨卷 stage/old/sidecar 只纳入 rescueInventoryHash 并保持原位，绝不作为会被整体移动的 runtime target；不得用未列路径藏唯一用户正文。同目录 marker 必填 `version,recoveryPrepareId,descriptorSha256,scope,state,updatedAt`，可变 target state 只写 marker 与中央 journal，不回写 immutable descriptor。prepare 在全部 user/runtime newStage manifests（包括不存在目标的 sidecar manifest）和当前 inventory 指纹验证后进入 `prepared`。

每次 recovery import 都必须先原子写独立 authoritative root marker `.linggan/recovery-imports/active.json`，不得把原事务 journal 当唯一 linkage。marker 与独立 recovery journal 必填 `{version,activeRecoveryImportId,kind,originRecoveryState,originalTransactionId,originalJournal:{state,sha256},descriptorSha256,state,terminalResult,supersedesOriginal,finalLiveFingerprint,supersessionEvidenceSha256,originalSupersedeState,updatedAt}`；originalTransactionId 在 data_missing、正常升级快照恢复等无原导入事务时为 null，originalJournal.state 只能是 `valid|missing|corrupt`，后两种 hash 为已保全原字节的 hash 或 null。prepare 时 terminalResult/finalLiveFingerprint/supersessionEvidenceSha256 为 null、supersedesOriginal 为 false、originalSupersedeState 为 `not_required`；该状态只能是 `not_required|pending|recorded`。originalJournal 及其 sha256 是整个 recovery transaction 的不可变输入：无论 valid/missing/corrupt 都绝不改写、补字段或镜像 recovery state。每次状态推进先写并复读独立 recovery journal，再写 root marker；root marker 允许落后一格，启动只能在 descriptor、recovery journal hash 与所有 target marker 一致时补齐，绝不能用新 hash 覆盖原 journal 证据。

restore_backup 完整成功时 terminalResult 为 `backup_restored`；restore_upgrade_snapshot 只有在 remigrate.state 已 verified、最终 app marker 和全部 live manifests 复验通过后，terminalResult 才为 `upgrade_snapshot_remigrated`。两种 completed 若 originalTransactionId 为 null，保持 supersedesOriginal:false/originalSupersedeState:not_required；若非 null，则必须在独占锁内复验原 journal hash、全部原 sidecar 的 rescueInventoryHash 和最终 live，先写不可变 `.linggan/recovery-imports/<recoveryPrepareId>/supersession-evidence.json`。evidence 固定 schema `{version:1,recoveryPrepareId,descriptorSha256,originalTransactionId,originalJournalSha256,originalEvidenceHash,terminalResult,finalLiveFingerprint,createdAt}`，originalEvidenceHash 等于冻结 rescueInventoryHash；文件用临时文件/fsync/rename/复读发布，完整 canonical JSON 的 SHA-256 就是 supersessionEvidenceSha256。随后把 finalLiveFingerprint、supersessionEvidenceSha256、supersedesOriginal:true、originalSupersedeState:pending 写入并复读 recovery journal/root marker。再原子写 `.linggan/recovery-imports/superseded/<originalTransactionId>.json`，固定 schema `{version:1,originalTransactionId,originalJournalSha256,originalEvidenceHash,recoveryPrepareId,recoveryDescriptorSha256,supersessionEvidenceSha256,createdAt}`；record 自身同样原子发布且同 original ID 已有不同字节时阻断。记录验证成功后才把 recovery journal/root marker 推进 originalSupersedeState:recorded。该设计不让 record 引用仍会从 pending 变为 recorded 的 marker hash，避免自引用或陈旧 hash。

原 journal/各卷 sidecar 保持只读证据，但普通事务扫描必须先验证 superseded record、immutable recovery descriptor、supersession evidence、original ID/hash/evidence 及 recorded 终态 marker 的字段一致性；recorded 后把原事务标为已归档并跳过原 manual_recovery，不再要求日后可变的 current live 等于 finalLiveFingerprint。崩溃发生在 evidence 发布后、pending 或 record 发布前时，服务仍关闭；启动只在当前 live 仍等于 evidence.finalLiveFingerprint 时补写 pending/record，否则阻断。recorded 后的恢复只验证不可变 record/evidence/descriptor 和 recorded marker 字段，不再比较 current live。只有 originalSupersedeState 已 recorded（或 not_required）才可归档 active pointer并开放服务。awaiting_upgrade_choice、ready_for_2_1、expired、rescue_rolled_back 以及未 verified 的 remigrate 始终 supersedesOriginal:false、finalLiveFingerprint/supersessionEvidenceSha256:null、originalSupersedeState:not_required。root marker 损坏/缺失但所有卷 descriptor/marker 能组成唯一同 ID 完整集合时，可先隔离坏 marker并重建；卷间不一致则阻断。hadLive:false 时物理 rescue 路径必须不存在，但 rescueManifestSha256 必须是 canonical `existed:false` target manifest 的非空 hash；hadLive:true 时 hash 必须匹配 live 的完整 byte manifest。root marker、descriptor、每卷 marker 和 recovery journal 都带完整 expected target 集合或其 descriptor hash，缺一即阻断，不能只从碰巧存在的卷推断范围。故障注入覆盖 evidence、final fingerprint、pending marker、superseded record、recorded marker、active 归档和首次开放服务后的正常写入；后续启动不得重新激活已被 recorded 证据取代的原事务。

preparing 或 prepared recovery import 在 24 小时后只能走 `preparing|prepared → expired`，且确认过期前从未发生任何 live→rescue。preparing 可以只有已写入 journal 的目标子集；清理范围必须来自已 fsync 的 immutable descriptor/marker，不能扫描猜测。过期收敛顺序固定为：在锁内复验所有已知 live/rescue 仍是 prepare 指纹 → 原子写 recovery journal 与 active root marker 的 expired 终态 → 把 `active.json` rename 为该事务内 `active.final.json` 并 fsync → `activeRecoveryImport:null` 且主状态回到 originRecoveryState → 最后按 descriptor 精确删除各卷 newStage/sidecar。崩溃在任一步时，启动根据 terminal journal/active pointer 幂等补归档或清理；pointer 未归档前不得删除唯一 descriptor，stage 先缺失或 live/rescue 变化则进入 manual recovery。prepared 一旦进入 rescue_importing 就清空 expiresAt；此后的 awaiting_upgrade_choice、ready_for_2_1、remigrate_snapshotting 与 remigrating_2_2 都不再按 prepare TTL 过期，只能按各自状态机完成或回滚。expired 后旧 ID 固定返回 410 `transaction_expired`，并重新允许 prepare；固定夹具覆盖 preparing/prepared、每个持久化点和“终态已写但 stage 尚在”。

recovery prepare 的 rescueInventoryHash 必须覆盖旧 `archive-jobs.json`、`.previous` 及其他 runtime sidecars 的原始字节，data_missing/queue-only 也不能把它们当可丢缓存。restore_backup 在最终固定 descriptor 之前按第 D2 节扫描队列：每段可识别 manualContent 先内容寻址写入 newStage，UID 存在于导入后 DATA 时进入该 entry 的成对 draft，UID 不匹配时进入 newStage orphans；损坏队列的全部原字节也以 runtime sourceScope 隔离。写入、fsync、复读后重算受影响 scope 的 new manifest，并把 `rescueOverlayHash` 作为非空 descriptor 字段。restore_upgrade_snapshot 的 rescueOverlayHash 固定为 null，不把当前 2.2 队列混入旧快照；当前 queue/previous 作为 runtime targets 进入各自 rescue，snapshot 中的 queue/previous 作为它们的 newStage 原样安装。只有所有唯一人工字节已进入受 v2 备份覆盖的 stage 或已验证 runtime rescue 后，成功提交才可替换旧队列。queue-only → restore_backup 在每个 draft、manifest、队列 target 持久点都有崩溃夹具；upgrade restore 则断言 snapshot 队列原字节与当前队列 rescue 原字节都可取回。

提交 token 复核后，在 authoritative root marker 与独立 recovery journal 中推进 `rescue_importing`，原事务 journal 始终只读。独立 recovery journal 的准备分支固定为 `preparing → prepared`、`preparing|prepared → expired`；提交分支固定为 `prepared → rescue_importing → rescue_committing → rescue_committed`。restore_backup 在全部新 live 复验后先完成第 14.2 节 finalLiveFingerprint 与 original supersession gate，再进入 completed；restore_upgrade_snapshot 进入 `awaiting_upgrade_choice → ready_for_2_1|remigrate_snapshotting|rescue_rolling_back`，ready_for_2_1 可在旧版停机后进入 remigrate_snapshotting 或 rescue_rolling_back，remigrate_snapshotting 只能进入 remigrating_2_2 或回到其来源选择态，remigrating_2_2 完成 supersession gate 后进入 completed，也可进入 rescue_rolling_back。失败回滚统一走 `rescue_importing|rescue_committing|awaiting_upgrade_choice|ready_for_2_1|remigrate_snapshotting|remigrating_2_2 → rescue_rolling_back → rescue_rolled_back`。所有 user/runtime target 先计算并持久化原 live 的 rescue manifest，状态为 `rescue_manifest_ready`；全部就绪后 recovery journal 才进入 `rescue_committing`。每个 target 的前向状态固定为 `rescue_manifest_ready → rescue_ready → new_live → new_verified`：`live → rescue` 后复验写 rescue_ready，`newStage → live` 后写 new_live，按来源 manifest 复验后写 new_verified。hadLive:false 时 rescue_ready 表示 live 已确认不存在。只有全部 target 都 new_verified 且原失败事务 artifacts 仍匹配 rescueInventoryHash，才能按 kind 进入下一状态。completed 后只重建 expected index、完整性缓存等可重建运行状态，不在事务外改写 queue、previous 或 app marker。completed、expired 或 rescue_rolled_back 时才把 `active.json` 原子 rename 为该 recovery transaction 内的 `active.final.json` 并 fsync；completed 且 originalTransactionId 非 null 时还必须先复验 originalSupersedeState:recorded，非 completed 终态保持 not_required。ready_for_2_1、remigrate_snapshotting 和 remigrating_2_2 都保留 active pointer 作为 2.2 再启动的阻断证据。活动指针消失后 `activeRecoveryImport` 才返回 null；启动必须幂等补完“终态已写但 superseded record/active 尚未归档”的窗口。未 supersede 原事务的 rescue 与原失败事务 artifacts 可作为普通 recovery generation 按 7 天/最多 2 组保留；一旦 originalSupersedeState 为 recorded，所有第 530 行启动验证依赖立即转入第 546 行永久审计代，完全豁免该清理规则。

启动看到 authoritative root marker 为非终态时必须读取 activeRecoveryImportId 及所有卷 descriptor/marker，并按状态分派，不能用一条“live 不等于原 new manifest 就回滚”的规则处理所有阶段。`preparing|prepared` 只按过期/继续 prepare 规则收敛；`rescue_importing|rescue_committing|rescue_committed` 才执行初始 swap 判据：每个 live 匹配 new manifest、每个 hadLive:true rescue 匹配 rescue manifest且原 artifacts 匹配 rescueInventoryHash时补齐 new_verified并前向完成，否则对全部 target 确定性回滚。`awaiting_upgrade_choice` 要求原 snapshot live 仍完整，异常字节先阻断并只允许 diagnostics 或经新状态指纹确认的 restore_rescue。`ready_for_2_1` 明确允许 2.1 任意改写 user/runtime live；2.2 在 legacy gate 后只计算并展示当前完整 fingerprint，绝不因它不同于原 new manifest 自动回滚。`remigrate_snapshotting` 只在新的 full snapshot 全部 fsync、manifest 验证且 recovery journal 已记录其 name/hash 后推进 remigrating；残缺且 live 仍等于 snapshotting 前指纹时清理残片并回到来源选择态，live 同时变化则保持阻断。`remigrating_2_2` 复验 remigrate full snapshot、app marker 与逐步迁移 journal，幂等续跑 pending step；任一项无法确定时保持该状态，允许 retry、diagnostics 或确认后的 restore_rescue，绝不套用原 snapshot manifest。回滚 target 状态为 `rescue_restore_ready → rescue_restored → rescue_verified`。hadLive:true 分两种合法旧态：若 live 已匹配 rescue manifest且 rescue 不存在，说明该 target 尚未执行第一次 rename或已恢复，必须优先直接补写 rescue_restored/rescue_verified，绝不能先隔离 live；否则必须由 rescue 匹配 manifest，新/未知 live 先按其 byte inventory hash 隔离到 `failedNew/<hash>/`，再执行 `rescue → live` 并复验。failedNew 是不可覆盖容器：同 hash 已存在且 manifest 相同则复用，不同 hash 并存。hadLive:false 时把任何 new live 以同样方式隔离后确认 live/rescue 都不存在。原失败事务 artifacts 也必须仍匹配 inventory。全部 rescue_verified 后，独立 recovery journal 与 root marker 写终态 `rescue_rolled_back`、`terminalResult:'rescue_restored'`、`supersedesOriginal:false`；原 journal 保持逐字节只读。随后把 active pointer 归档并清除，主恢复状态回到 descriptor 的 originRecoveryState，`activeRecoveryImport:null`，并重新允许新的 recovery prepare/import。若在终态 journal 与 pointer 归档之间崩溃，启动复验全部 rescue 后只补归档，不再次 rename；其他磁盘组合保持非终态并阻断普通 API。descriptor 缺任一预期 target 时同样不得猜测。固定故障注入覆盖 missing/corrupt 原 journal、root marker 重建、全局进入 rescue_committing 后第一处 rename 前，以及每个 scope 的 `live → rescue`、`newStage → live`、`live → failedNew`、`rescue → live` 后立即崩溃，含 failedNew 已存在及 journal/marker 各落后一格、全新态完成、awaiting/ready/remigrate_snapshotting/remigrating 分派、全 rescue 恢复、终态已写/active 未归档和下一次 prepare；结果不能是混合 scope或永久卡死。

machine-wide mutex 只约束 2.2 合规进程，不能假定仍运行的 2.1 会配合。任何用户数据读写前先执行 legacy quiescence gate：用已解析但尚未创建的 canonical roots 做只读进程审计，保守识别所有本机用户下的旧 LingganLauncher、缓存 Node 和 `node ... server.js`；同路径、命令行不可读、权限不足或疑似旧实例都返回 `legacy_instance_may_be_running`，不得继续。随后先在 `127.0.0.1` 绑定配置端口为 bootstrap/recovery listener并保持同一 socket；EADDRINUSE 时只探测 health/version 并提示关闭旧程序，不触碰数据。首次非 fresh 升级还要求用户在该 listener 明确确认“所有旧版本已关闭”，确认绑定 canonical root hashes、进程审计摘要和 bootId；它只解锁本次仍持有 listener 的启动，不能跨重启复用。若平台无法审计共享根的其他用户进程，则 fail closed 并要求重启后在启动任何旧版前执行升级。支持边界明确为“2.2 进程强互斥；2.1→2.2 必须完成停机门禁”，不承诺阻止用户在门禁后手工再启动不合作旧版。固定夹具覆盖同端口、不同端口、不同用户、命令行拒读和双 launcher，断言任何失败都发生在 snapshot/marker/scaffolding 之前且 DATA SHA 不变。

Windows launcher 必须删除现有 `PrepareDataDirectory` 类预写职责：它只可在用户数据根之外准备版本化运行缓存、解析并传递路径、启动 Node 与显示 bootstrap 状态；不得 mkdir DATA/entries/CONTROL roots，不得复制 `DATA.example.md`，不得写 queue、marker、snapshot 或 lock-parent。源码入口遵守相同边界。所有用户目录初始化只能由 Node 在 quiescence gate、preexisting inventory、kernel mutex 和资源锁之后执行。Windows packaged 测试用 marker-only、queue-only、DATA missing+old generation 和两个并发首启夹具证明 launcher 启动前后证据不被示例 DATA 遮蔽。

启动顺序固定为：解析并验证存储 topology → legacy 进程审计并绑定 bootstrap listener → 只读记录 preexisting inventory → 按序取得全部 machine-wide volume mutex → 创建/验证固定 CONTROL lock-parent scaffolding并取得 CONTROL_DIR 资源锁 → 创建其他空 lock-parent scaffolding并取得其余 resource locks → 复扫 inventory 排除本次空 scaffolding后确认未变 → 扫描/恢复全局 journal → 恢复结果 entries 中的 archive transaction markers → 判定 fresh install → 按判定初始化或进入恢复 → 创建并验证 fresh marker 或应用升级快照 → 执行或恢复 data schema 与 UID 迁移 → 执行首次 2.2 迁移或每次启动的降级兼容扫描 → 以 `autoStart:false` lazy 创建 capture/ArchiveService → 按恢复结果 reconcile 队列 → 将同一 bootstrap listener 提升为完整服务 → 启动队列和消息适配器。fresh install 只有在 DATA、全部用户根和全部可恢复/安装证据都不存在时成立；证据包括 import/archive sidecar、old/stage/runtime-old generation、upgrade snapshot、保护代、recovered-orphans、活动 `archive-jobs.json`/`.previous`、app migration marker、idempotency receipts、archive-attempts、expected index、完整性缓存，以及 CONTROL_DIR 中任何其他预先存在的普通文件或非空目录。终态 journal 仍指向可验证 old 时也不是 fresh；只有 preexisting inventory 中的空目录可忽略，本次 scaffolding 不可反过来改变判定。fresh 时先把 `DATA.example.md` 以临时文件、fsync、rename、复读原子初始化为 DATA，再原子写第 14.3 节完整 fresh app marker；若崩溃在 DATA 成功而 marker 写入前，下次因 DATA 已存在按普通首次升级先创建并验证快照，不能判 data_missing。DATA 缺失但发现任一其他用户字节或安装证据时进入 `data_missing` 恢复模式，由 status 列出候选，不能用示例数据遮蔽恢复线索。固定夹具覆盖 queue-only、marker-only、idempotency-only、“DATA 已写/marker 未写”和“completed + live 缺失 + old 有效”。任何恢复或升级迁移失败只保留 bootstrap recovery shell。

originalSupersedeState 进入 recorded 时，必须把 superseded record、supersession evidence、immutable recovery descriptor、独立 recovery journal、`active.final.json` recorded 终态 marker、全部卷 recovery target marker，以及它们引用的原 journal/全部卷原 sidecar 登记为同一组不可拆分审计代；第 530 行启动验证只能依赖这一完整集合。v2.2 不自动删除、改写或单独移动其中任何一项，也不套用普通 recovery generation/old 的 7 天或 2 组清理。未来若提供清理，必须在全局锁内先证明原事务和该 recoveryPrepareId 已不再被任何 active/final recovery、WAL、app marker 或升级快照引用，并以独立 cleanup journal 对整组逐项删除；record、descriptor、recovery journal 或 recorded marker 都不能先于最后一份被引用证据消失。若该集合任一项缺失、hash 不符或字段不一致，启动保持恢复模式，不得退回原 manual_recovery 后继续写入。

### 14.3 应用升级快照与降级

非 fresh 首次运行 2.2 且 `.linggan/app-migrations/2.2.0.json` 不存在时，先在 `.linggan/upgrade-snapshots/pre-2.2.0-<UTC>/` 建立目录镜像和 SHA-256 manifest。快照覆盖 `DATA.md`、entries、brainstorms、trash、recovered-orphans，以及迁移前原始 `archive-jobs.json`/`.previous`；后两项仅用于恢复 2.1 的待处理人工正文，不进入普通用户备份。snapshot manifest 是固定字段顺序、无额外空白的 UTF-8 JSON：`{version:1,kind,restorable,appVersion,createdAt,targets,runtime}`。完整升级前快照必须是 `kind:'pre_upgrade_full',restorable:true`，targets 按 scope 排序且必须恰好包含 `data|entries|brainstorms|trash|orphans` 各一次。targets 也使用固定联合：data 文件目标为 `{scope:'data',rootType:'file',existed,bytes,sha256}`；四个目录目标为 `{scope,rootType:'directory',existed,fileCount,totalBytes,files}`，files 按规范相对目录路径排序且每项固定 `{path,bytes,sha256}`。不存在的文件目标使用 bytes:0/sha256:null，不存在的目录目标使用 fileCount:0/totalBytes:0/files:[]；存在时所有计数/hash 必须与复读字节一致，文件目标不使用空路径、`.` 或 basename。runtime 固定 `{files}`，只允许逻辑名 `archive-jobs.json|archive-jobs.json.previous`，每项固定 `{name,existed,bytes,sha256}`；不存在时 bytes 为 0、sha256 为 null。manifest 不含可移植性差的绝对路径，restore 时按 scope 映射当前已验证 topology；所有字节和不存在状态复读一致后才视为有效。

app marker 固定 schema 为 `{version:1,appVersion:'2.2.0',freshInstall,snapshotPath,snapshotManifestSha256,steps,compatibilitySweep,completedAt}`；steps 固定 `{dataSchema,manualDrafts,canonicalContent,lifecycle}` 且每项只能 `pending|completed`，compatibilitySweep 固定 `{lastRunAt,resultHash}`。fresh 初始化时两个 snapshot 字段、两个 sweep 字段与 completedAt 先为 null，四步先为 pending；只有 freshInstall:true 才允许 snapshotPath/hash 为 null。非 fresh marker 必须引用刚刚复验的 snapshot path/hash。每步完成后原子更新，四步均完成才写规范 UTC completedAt；marker 缺字段、状态倒退、fresh 与磁盘证据矛盾或非 fresh snapshot 无法复验都进入恢复模式，不能因“文件存在”就跳过快照或迁移。

每个从 2.1 数据进入 2.2 的迁移周期只生成一份成功的不可变 `pre_upgrade_full`，同一安装允许多个周期快照并存；常规首次升级名为 `pre-2.2.0-<UTC>`，从 ready_for_2_1 再迁移名为 `pre-remigrate-2.2.0-<recoveryPrepareId>-<UTC>`。当前 app marker 必须指向本周期 snapshot path/hash，active recovery journal 另记录 remigrate snapshot name/hash。任何仍被 app marker、recovery journal、WAL 或 active/final recovery descriptor 引用的 full snapshot 永不自动删除；v2.2 不提供删除 full snapshot 的 API 或 CLI，未引用代也只列入占用提示而不自动清理。失败的临时快照不写 marker并保持来源选择态或进入恢复模式。快照或 fresh marker 验证后首先运行可重入的 data schema/UID step：为 legacy DATA 分配稳定 UID，并按既有迁移规则把数字条目目录复制到最终 UID 目录；原目录在整次应用迁移完成前保留为恢复证据。只有该 step 的 DATA 与目录映射复读验证并标记 completed 后，才能运行任何按 UID 扫描队列、正文、archive 或保护代的步骤。随后 canonical 正文转换、旧队列人工正文提取和生命周期写入各自写可重入 migration step；重启可安全重复。

app marker 已完成也不能跳过兼容扫描；但扫描开始前必须确认 dataSchema step 已完成，不能按尚未分配的 UID 猜测目录归属。每次 2.2 启动在服务开放前扫描根级 `content.md`、队列中的 `manualContent`、每个 archive 的 manifest/metadata/expected-index，以及 `protected-generations/current.json` 与 current 保护代的完整性和 active/current 字节一致性；这些都是从 2.1 常规降级、磁盘损坏或中断写入后再启动的识别信号。发现任一项时，先建立 `.linggan/upgrade-snapshots/post-downgrade-<UTC>/` 增量快照（DATA、受影响 entry 与原队列）并验证。增量 manifest 使用同一 schema，但必须是 `kind:'post_downgrade_incremental',restorable:false`，targets 只列实际包含的非空 scope 子集；它只用于候选保全和诊断，永远不能进入 restore prepare。active 健康但 current 缺失/损坏时，从 active 以归档事务原子重建保护代；current 健康但 active 缺失/损坏或二者完整却不一致时，保护代恢复为 canonical 活动版，原 active 全部普通字节按内容 hash 保存在 `attachments/post-downgrade-content-<hash>.md` 与 orphan 容器，显示为待用户比较的 `downgrade_candidate`，绝不覆盖受保护正文；二者都无有效代或重建失败时进入恢复模式，不启动归档队列。没有保护代的 2.1 新建条目只有在 active 正文可用时才能作为 `legacy_unknown` 建立自洽 manifest 和首个保护代，不可用内容只隔离。随后提取队列草稿、转换根正文，并把 `compatibilitySweep.lastRunAt/resultHash` 写入 marker。增量快照保留 30 天且最多 2 组，但 canonical 保护代及已保全的 2.1 候选不随该期限删除。稳定演练必须覆盖 current 缺失、active 缺失、二者错配时各写入点崩溃，以及 legacy DATA 无 UID + 数字 entries 目录先迁移再扫描、2.1 新增根正文、队列尚存人工正文、人工归档已成功且队列已清、自动归档覆盖优质 2.2 正文并经过超过 30 天；再升级后 2.2 前态与 2.1 新字节都必须可取回，活动正文不得质量倒退，所有正文与草稿必须归属迁移后的正确 UID。

常规降级只替换为 2.1 程序并保留当前数据，因为 `DATA.md` 仍是版本 2。只有数据损坏或迁移不兼容时，才由 2.2 恢复界面或同进程 interactive `recover.js` 在明确确认后恢复 pre-2.2 快照；恢复前尽可能先导出当前 2.2 救援备份。CLI 的只读 `--list-upgrade-snapshots` 可显示 kind/restorable；任何 restore/finalize 必须进入 `recover.js --interactive`，先在同一持锁进程展示 snapshot manifest hash、完整 stateFingerprint 和随机 challenge，再由该进程生成并立即消费一次性 token。本版不提供可脚本化的离线 restore、`--force`、`--confirm <manifestSha256>` 或 `--confirm <token>`；自动化只能以认证客户端调用正在运行的 recovery API，先 GET status 获取当次 token。UI 使用两阶段 `POST /api/recovery/restore-upgrade-snapshot/prepare` 与 `POST /api/recovery/restore-upgrade-snapshot`，列表同时显示完整与增量快照，但 prepare 只能接受 hash 匹配、kind 为 pre_upgrade_full、restorable:true 且五 scope/runtime 均完整的快照；其他情况以 `snapshot_not_restorable` 零写入拒绝。绝不自动选择“最新”，也不把“回退程序”自动解释为“覆盖 2.2 期间新增的数据”。

升级快照恢复不得直接逐根复制，而是第 14.2 节 recovery-import 协调器的 `kind:'restore_upgrade_snapshot'`。prepare 只接受完整 pre_upgrade_full，把 snapshot 中 DATA、entries、brainstorms、trash、orphans 的原始字节映射到每个 live 同卷的五个 user newStage，不提前做 2.2 canonical migration；snapshot queue/previous 原始字节分别进入两个 runtime newStage，app_marker runtime target 为 newExists:false，当前 2.2 app marker进入其 rescue。原失败事务 sidecars 保持原位并只进入 rescueInventory。每个 target 都使用自己的 descriptor 副本、manifest、marker、newStage/rescue/failedNew 和逐 rename state；全部 user/runtime stage 的容量、fsync、hash 与 snapshot manifest 验证通过后才进入 prepared，`GET recovery/status` 才签发绑定 recoveryPrepareId、snapshotName/hash 和全部 target 指纹的 token。WAL domainRef 必须指向 recoveryPrepareId，不能指向易变 snapshotPath。

全部 user/runtime target new_verified 后，restore_upgrade_snapshot 不写 completed，而进入稳定阻断态 `awaiting_upgrade_choice`；active pointer 保留，服务只提供 recovery status/diagnostics/finalize，不启动队列、消息入口或普通数据 API。此时活动 user roots 与 queue/previous 必须逐字节等于 snapshot，2.1 待处理人工正文因此仍能被 2.1 识别；当前 2.2 用户根、队列和 app marker 全部保留在逐 target rescue 中。`POST /api/recovery/finalize-upgrade-restore` 是确认型动作，固定 mode 为 `restart_2_1|remigrate_2_2|restore_rescue`。restart_2_1 复验全部 snapshot live 后写并复读 `ready_for_2_1` 与 WAL receipt，保留 active pointer，再优雅退出并最后释放 mutex；2.2 再启动时看到该状态仍停在 recovery shell，legacy gate 确认 2.1 已关闭后才允许后两种 mode。

remigrate_2_2 可从 awaiting_upgrade_choice 或 ready_for_2_1 开始。它先在 recovery journal 写固定对象 `remigrate:{sourceState,sourceFingerprint,snapshotName,snapshotManifestSha256,state}`，其中 state 依次为 `snapshotting|snapshot_ready|migrating|verified`，然后进入 `remigrate_snapshotting`；sourceFingerprint 覆盖当下全部 user/runtime live。它创建本周期唯一 `pre-remigrate-2.2.0-<recoveryPrepareId>-<UTC>` full snapshot，逐文件写入、fsync、复读并验证五 scope/runtime，成功后才填 snapshotName/hash、写 state snapshot_ready 和完整 pending app marker，再推进 `remigrating_2_2`。迁移按 14.3 的 dataSchema/manualDrafts/canonicalContent/lifecycle 顺序，每步都以 app marker 和 recovery journal 双重记录并可重入；启动在 snapshot/hash/source 与已完成步骤可验证时只续跑下一步。全部完成且活动数据/保护代/队列复验后，依次写 remigrate.state verified → 计算并持久化 finalLiveFingerprint → 写 terminalResult `upgrade_snapshot_remigrated` → 有原事务时按第 14.2 节完成 supersedesOriginal pending、superseded record 和 recorded 三步（无原事务保持 not_required）→ 写 recovery completed → 归档 active → 最后开放服务；在 recorded/not_required 之前禁止监听完整数据 API，任一步崩溃都从已复读的上一状态幂等补齐。snapshotting 失败且 live 仍等于 sourceFingerprint 时只清理残片并回到 sourceState；live 同时变化、snapshot 损坏或迁移状态无法判定时保持恢复 shell，允许 retry 或确认后的 restore_rescue。remigrating_2_2 不按原升级快照 new manifest 回滚。

restore_rescue 可从 awaiting_upgrade_choice、ready_for_2_1、remigrate_snapshotting 或 remigrating_2_2 执行：先把 2.1 运行期或部分再迁移产生的全部当前字节按 failedNew 内容寻址规则保全，再对全部 user/runtime target 执行 rescue 回滚，复验后回到 originRecoveryState；remigrate full snapshot及其 marker 继续按引用保留。三种 mode 的 token 指纹覆盖 mode、原 snapshot、当前 live/rescue、remigrate 对象（如有）与 recovery state。离线 CLI 只通过前述同进程 interactive 菜单调用这些相同动作；`--create-rescue` 只是交互前额外尝试导出当前有效 v2 包，事务自己的 rescue generation 始终强制。故障注入覆盖每个 user/runtime target 的 stage、live→rescue、newStage→live，以及 awaiting、ready 跨重启、2.1 改写后回到 2.2、source fingerprint、remigrate full snapshot 每个文件、pending app marker、四个迁移步骤、三种 finalize、WAL receipt、restore_rescue 和 active 归档后的每一步崩溃；只允许完整当前代、完整原快照代、完整 remigrate source代或保持阻断，不能出现混合代或丢失任一队列正文。

### 14.4 生命周期与待处理判定

7、14、30 天均按 UTC 固定毫秒计算：`days * 86_400_000`；完成时的默认回顾日从服务器确认状态变更的 `now` 加 30 天，不按日历月。`set_review` 只接受规范 UTC 毫秒格式，且范围为服务器 `now` 到 `now + 10 * 365 * 86_400_000`（含边界）。

`lifecycle_missing` 仅在 `createdAt` 缺失、非法或重复时成立；`lastStudiedAt`、`nextReviewAt` 合法缺失不触发。最近活动定义为 `lastStudiedAt ?? createdAt`；两者都没有时不命中 `stalled` 或 `unresearched`。开始研究只指现有状态从“待研究”变为“进行中”。

状态与动作的时间变更表固定为：

| 事件 | `createdAt` | `lastStudiedAt` | `nextReviewAt` |
| --- | --- | --- | --- |
| 新条目首次写入 | 若无则 `now`，以后不改 | 不改 | 不改 |
| 待研究 → 进行中，或已完成 → 进行中 | 不补历史值 | `now` | 清空 |
| 任意状态 → 已完成 | 不补历史值 | `now` | 原值 `> now` 则保留，否则设 `now + 30天` |
| 已完成 → 待研究，或进行中 → 待研究 | 不改 | 不改 | 清空 |
| 保存实质研究内容 | 不补历史值 | `now` | 若当前已完成则设 `now + 30天`，否则不改 |
| `mark_reviewed` | 不补历史值 | `now` | 设 `now + 30天` |
| `set_review` / `clear_review` | 不改 | 不改 | 设为请求值 / 清空 |

重复提交同一 `requestId` 不再次移动时间；仅打开、抓取、计时、失败保存或再次提交未改变的状态不更新时间。历史条目第一次真实研究只建立可信的 `lastStudiedAt`，不能冒充未知的创建时间。

“实质内容”先 trim，再排除精确占位集合 `['', '（待补充）', '待补充', '暂无', '无']`。研究有内容是 `DATA.md` 的“研究要点”，或 `notes.md` 的 `keyFindings`、`actionItems`、`conclusion`、`experience` 任一为实质内容；`open_action` 仅看 `actionItems` 且状态不是“已完成”。`unresearched` 必须是待研究、createdAt 已知、`now - createdAt >= 7 天` 且上述研究内容全部为空。`stalled` 必须是进行中、活动时间已知且 `now - activity >= 14 天`。

重复或非法生命周期注释原样保留并进入健康诊断。普通笔记保存仍先提交正文，然后返回 `saved:true,lifecycleUpdated:false,warning:'invalid_lifecycle'`；除修复外的专用 lifecycle 动作返回 409，不能顺手改坏数据。`repair_lifecycle` 是此状态下唯一允许的动作：`createdAt` 保留文件顺序中的第一个合法值，可变字段保留最后一个合法值，删除同键其余非法/重复注释；没有合法值时保持缺失，不发明时间。其他动作仍为 `set_review`、`clear_review`、`mark_reviewed`。

待处理条目的主排序键依次为：最小 priority；该优先级原因中最早的非空 `dueAt`（空为正无穷）；活动时间从早到晚（空为正无穷）；按点分整数比较的 ID，再按原始 ID 字符串。`review_due.dueAt = nextReviewAt`，`stalled.dueAt = activity + 14 天`，`unresearched.dueAt = createdAt + 7 天`；其他原因无 dueAt。

`archive_blocked` 包含 `failed`、`manual_required`、`manual_pending`，以及没有 queued/running 任务的 `not_archived`。`partial` 仅在 `retryable === true`、正文不可用或完整性为 `damaged` 时命中；只有可选 raw HTML/图片缺失、或低质量候选被安全拒绝且旧正文可用时不命中。`unchecked`、`unverified` 本身不等于损坏。

attention 读取 notes 失败或超过 20 MiB 时保留该 DATA 条目，只忽略 notes 派生的“研究有内容”和 `open_action`，继续计算 lifecycle 与 archive 原因，并在 item 及顶层 `warnings` 返回 `notes_unreadable` 或 `notes_too_large`；不得创建模板。reasons 固定按 priority、code 排序。响应 counts 固定为 `{items,byReason,warnings}`，`byReason` 含六个原因码且统计命中条目数；非法点分整数 ID 不进入 items，并记录 `invalid_id`。只有 DATA 本身不可读或 schema 无法建立唯一条目集合时，整个 attention API 才返回 `attention_unavailable`，不影响独立 `/api/data` 的错误处理。

### 14.5 归档质量、并发与完整性

规范化算法固定为：统一 CRLF 为 LF；仅当第一行精确等于当前 metadata title 组成的 `# <title>` 时删除该行；随后删除空行及连续匹配 `> 来源:`、`> 作者:`、`> 摘要:` 的应用包装行；把 Unicode `White_Space` 连续段折叠为一个空格并 trim；用 Unicode code point 数而非 UTF-16 code unit 数计长。scraper 自己正文中的其他 H1 或引用不得删除。自动正文少于 40 个 code point、为空，或等于占位 `> 暂无可用正文，请手动补录内容。` 的规范化结果时不可用。人工正文只要求 trim 后非空且不是占位，可显式保存短内容。

质量状态等级是 `usable_clean(2) > usable_partial(1) > unusable(0)`。正文可用但 scraper 报 partial 或缺少可选 raw/image 时为 `usable_partial`；正文不可用、failed、manual_required 为 `unusable`。无旧正文也只接受状态至少为 `usable_partial` 的候选，不能因 failed 响应附带非空错误页就接受。authority 只能是 `manual(5)`、`official_api(4)`、`official_raw(4)`、`site_scraper(3)`、`readability(2)`、`metadata(1)`、`placeholder(0)`；scraper 必须显式返回，不能从 source 文案猜测。`legacy_unknown` 是 manifest 可表示但不参与数值比较的保护值，只用于旧活动正文，只允许人工替换。

同一 UID 的手动与自动提交共用 mutex。候选在拿到 UID 锁后重新读取活动 manifest，再比较和提交，所以两个并发“首个候选”只有先通过者能按无旧正文规则处理。质量拒绝返回 `{state:'partial',retryable:false,reasonCode:'candidate_lower_quality'}`，只更新 `.linggan/archive-attempts.json`，活动目录及 manifest hash 必须逐字节不变；canonical 冲突返回同样不可重试的 `legacy_content_conflict`，但它随 canonical 目录事务进入新 metadata。两者都不得进入普通退避重试。

首次迁移以 `entries/<uid>/archive/content.md` 为唯一正文：根级正文单独存在且可用时转为 `legacy_unknown`；两处字节相同则校验 archive 后移除冗余根文件；两处不同则保留 archive 为活动版，把根级字节移入 `attachments/legacy-content-<sha256前12位>.md` 并记录冲突；只有根级文件但正文不可用时也移入 attachments 并记录 `legacy_content_unusable`，活动状态为 `not_archived`。转换前后均拒绝特殊文件，写入、复读和 manifest 验证成功前不删除根文件。`/api/entry/scrape`、正文 GET/POST、`search.js` 和 `brainstorm.js` 全部调用 `archive-content.js`/ArchiveService；任何调用方不得再读写根级正文。回归测试迁移后删除根文件，搜索与头脑风暴仍必须命中 canonical 内容。

归档 manifest v1 的必填字段固定为 `version:1`、小写 UUID v4 `snapshotId`、规范 UTC 毫秒 `createdAt`、`quality` 和 `files`。quality 必填 `manual:boolean`、上述 authority、quality state、非负整数 `normalizedChars`；files 必填规范相对 `path`、非负整数 `bytes`、小写 SHA-256 和 `provenance`，provenance 只能是 `fresh`、`inherited`、`legacy_unverified`、`manual`。files 按路径 UTF-8 字节排序且不含 manifest 自身。manifest canonical JSON 的字段顺序就是上述顺序、无额外空白，`manifestHash` 为其 UTF-8 SHA-256。

`content.md` 与 `metadata.json` 必须存在。metadata schema 固定为 `{archiveSchemaVersion:2,snapshotId,entry:{uid,id,url,title},capture:{state,authority,manual,capturedAt,source},migrationWarnings:[]}`；capture state 只能是 `succeeded|partial|manual`，capturedAt 为规范 UTC，authority 与 manifest 相同，source 是最长 200 字符的显示文本，warnings 只允许稳定 `legacy_content_conflict|legacy_content_unusable|downgrade_archive_rewritten` 并按字典序排列。metadata 不得记录会在拒绝后原地变化的 lastAttempt。被拒候选的运行 sidecar schema 固定为 `{version:1,items:{<uid>:{attemptedAt,state,reasonCode,retryable,candidate:{authority,state,normalizedChars}}}}`；reasonCode 只允许 `candidate_lower_quality|invalid_authority|candidate_unusable`，不保存候选正文。

archive validator 必须在任何质量比较前完成交叉校验：`content.md` 用 fatal UTF-8 解码且受 20 MiB 上限；manifest.snapshotId、metadata.snapshotId、保护目录 snapshotId（如适用）完全相等，metadata.entry.uid 与条目目录/Data UID 完全相等；manifest.createdAt 等于 metadata.capture.capturedAt；manifest quality 的 manual/authority 与 metadata.capture 完全相等。`manual:true` 当且仅当 authority/capture state 为 `manual`；自动或 `legacy_unknown` 必须 manual:false 且 capture state 为 `succeeded|partial`。活动 snapshot 的正文必须按 14.5 算法重新规范化并重算 Unicode code point 数，结果必须等于 normalizedChars 且正文达到对应人工/自动可用门槛；manifest 中不得信任自报字符数。capture state 为 partial 时 quality state 必须是 `usable_partial`，其余 state 也要按正文和可选产物重新推导为 `usable_clean|usable_partial`，活动 manifest 不允许 `unusable`。metadata 所有对象拒绝未知字段，id/url/title 只作为捕获时快照，不要求等于后来可编辑的 DATA 值。任一不一致都视为 `invalid_manifest`，不能进入 60% 比较或成为保护代。

继承旧可选产物前必须 `lstat` 为普通文件，并通过对应 magic、JSON 或有界 gzip 校验；每个继承记录标记 `provenance:'legacy_unverified'`。新活动归档除 manifest 外的每个普通文件必须恰好列一次，不得有额外文件。damaged 原因码全集固定为 `missing`、`missing_manifest`、`unreadable`、`checksum_mismatch`、`invalid_manifest`、`unexpected_file`、`unsupported_file_type`；符号链接/reparse 不跟随。

归档目录事务使用 `entries/<uid>/.archive-stage-<snapshotId>/`、`.archive-old-<snapshotId>/`、`protected-generations/.stage-<snapshotId>/` 和 `.archive-transaction-<snapshotId>.json`。marker 必填 `version,uid,snapshotId,state,stage,live,old,stageManifestHash,oldManifestHash,protectedSnapshotId,protectedManifestHash,updatedAt`，前向 state 为 `stage_ready|protected_ready|old_ready|live_ready|verified|completed`，回滚 state 为 `rollback_ready|old_restored|old_verified|completed`。顺序固定为：验证候选 → 写并验证 immutable 保护代 → 交换活动 archive → 验证活动 archive → 原子更新 current 指针 → completed；回滚时 current 仍指旧保护代，未成为 current 的新保护代只在旧活动版复验后清理。动作与 fsync 顺序复用 14.2，且每个 UID mutex 内启动时先恢复 marker 再处理队列；每个状态推进点都有崩溃夹具。

完整性缓存项必须同时匹配 `uid`、`snapshotId` 和 manifestHash；否则状态为 `unchecked`、`checkedAt:null`。本地扫描后才写 `healthy` 或 `damaged` 与 `checkedAt`；无活动目录为 `not_archived`。只有升级时登记为 `legacyNoManifest:true`，且 metadata、事务 marker、expected index 都没有 v2 snapshot 证据的旧目录才是 `unverified`。若 `metadata.archiveSchemaVersion:2`、事务 marker、既有缓存或 `.linggan/archive-snapshots.json` 表明曾有 manifest，而 manifest 缺失，则必须是 `damaged/missing_manifest`。该 expected index 原子维护、普通备份中排除但在导入后从 manifests 重建。归档 commit、导入、回滚和 canonical 迁移在同一事务中更新 expected index 并失效旧缓存，旧 snapshot 的 healthy 结果不能套用到新内容；删除 v2 manifest 的回归夹具必须断言 damaged 并进入 `archive_blocked`。

全局 namespace 用每请求独立 WAL，而不是并发改写一个 JSON：`.linggan/idempotency/<requestId>.json` schema 固定为 `{version:1,requestId,action,requestHash,state,fixedNow,beforeFingerprint,afterFingerprint,domainRef,httpStatus,response,createdAt,completedAt}`。state 只能 `pending|committed`；执行前先确定服务器时间、事务/任务 ID、完整 proposed bytes 或 domain journal 引用及 before/after fingerprint，写入并 fsync pending，之后才允许第一次领域写。lifecycle 必须在 WAL 中保存 fixedNow、原 DATA hash 和已完整渲染的新 DATA hash；DATA fsync 后、receipt 前崩溃时，启动看到 after hash 就补 committed 并重放同一 lifecycle，看到 before hash 才用原 fixedNow 重试，不能再次顺延 30 天。backup/archive/recovery 动作同理由各自 transaction/task journal 或完整 before/after hash 判定。

启动在开放数据 API 前逐个 reconcile pending：当前状态等于 after 或领域 journal 已有终态时补写固定 httpStatus/response；等于 before 时保持可安全重试；两者都不符就进入 `idempotency_recovery_required`，不得猜测。committed receipt 原子写并复读后，才向客户端返回已发生写入的结果。持久化 token-free 的 2xx、已发生写入后的终态 409/410/500；纯校验 400/413、认证错误、423/503、507 和 `transaction_busy` 不落 WAL。committed 保留 7 天或最近 2000 条（先到者），pending 在明确收敛前永不按时间删除。重启对相同 action/requestHash 重放完全相同的 token-free HTTP status/body；人工正文、bundle、confirmation token 与 Cookie 永不进入 WAL。

confirmation 只由当前持锁进程的 status/token 服务在内存新发：HTTP 客户端通过 `GET /api/recovery/status` 获取，offline interactive CLI 在展示同一 status 与随机 challenge 后于本进程生成并立即消费。因此任何 idempotent 写响应都不得包含 token；备份 recovery prepare 与升级快照 prepare 的重复/跨重启响应都只重放各自的 ID、hash、summary、expiresAt，HTTP 客户端随后重新 GET status，interactive CLI 则重新开始本轮 challenge。pending 的确认型动作若尚未写入，继续执行前必须提交当前状态对应的新 token；若领域状态已证明完成，则直接补 receipt，不再次要求或持久化旧 token。

`clear-stale-lock` 是唯一例外：lock-conflict shell 未持有共享数据锁，不读写上述 WAL。它以 one-time token 和完整 evidence 尝试清理前，必须先赢得按序排列的全部 machine-wide volume mutex；输掉任一 mutex 就释放已取 mutex 并返回不缓存的 409。赢家在 mutex 内重算 evidence，只能执行一次 `rename(final,unique-quarantine)`，随后永远只按唯一 quarantine 路径删除并正常 `mkdir(final)` 获取资源锁；证据变化、rename 目标已不存在或重抢 EEXIST 都返回 409，绝不再触碰 final。只有取得全部资源锁的实例才返回 200 并转入正常服务。该 requestId 仅用于日志关联，不承诺跨重启重放。两个 OS 用户/两个 lock-conflict shell 在 detach、quarantine 删除、新 owner mkdir 和 owner 复读各暂停点交错的夹具必须断言最多一个 200、新 owner 从不被旧证据删除，且只有赢家能写全局状态。

### 14.7 自动化、产物提升与发布证据

高风险逐文件覆盖集合固定为 `lib/backup.js`、新建的 `lib/backup-format.js`、`lib/backup-transaction.js`、`lib/maintenance.js`、`lib/archive-content.js`、`lib/archive-quality.js`、`lib/archive-integrity.js`、`lib/attention.js`，以及现有 `lib/schema.js`、`lib/store.js`、`lib/archive.js`、`lib/archive-queue.js`、`lib/capture.js`、`lib/search.js`、`lib/brainstorm.js`。这些文件的 statements、branches、functions、lines 四项都必须逐文件不低于 90%，命令使用 c8 的 `--check-coverage --per-file` 四项阈值；不得靠排除失败分支过门禁。

`package.json` 固定提供 `test:scrapers:fixtures`、`test:e2e`、`test:launcher` 和覆盖命令。固定夹具不得访问外网；E2E 发现任何真实 `DATA.md` 路径立即失败。`test:launcher` 进入每个 Windows PR 和候选门禁。Windows PR 用夹具 payload 验证编译；最终候选 workflow 在指定 commit 上执行完整 `package:exe` 一次，随后对生成的同一 EXE/ZIP 执行 smoke、恢复演练、内容扫描和 SHA256SUMS 复核。

候选 commit 必须把 Node 24 精确版本、官方 URL 和 SHA-256 固定在 `scripts/runtime-node.json`，构建只能读取该文件，执行时不解析“latest”。发布 allowlist 固定列在 `scripts/release-allowlist.txt`；ZIP/EXE 解包后出现 `DATA.md`、`docs/entries/**`、`.linggan/**`、`archive-jobs*`、`.env`、测试 sentinel secret、Cookie/API token/企业微信或钉钉 secret 模式，或任何 allowlist 外路径都失败。Windows 恢复演练使用 `LINGGAN_DATA_DIR` 临时目录，覆盖 2.1 fixture 升级、v1/v2 导入、锁文件导致的安全回滚、二次启动和 2.1/2.2 再升级；鉴权门禁覆盖非回环地址、伪造 Host、未登录 API 与 CSRF。

稳定发布不是 tag 触发的重建：受控 workflow 接收版本与完整 commit SHA，先完成全部门禁并保存不可变产物及 hash，再由最后一个 job 创建 tag、draft Release、上传并回读校验资产，最后公开 Release。仓库配置 `v*` tag ruleset，bypass 列表只含专用 Release GitHub App；App 私钥放在需人工审批的 protected environment，最终 job 才签发仅目标仓库、短时、最小 `contents:write` token，其他 job 的 `GITHUB_TOKEN` 始终 `contents:read`。Release 上传的每个字节必须与已测试 artifact hash 相同。tag 后任一步失败都由同一 App 按“删除未公开 Release → 删除本次 tag → GET ref 确认 404”补偿；补偿本身失败则记录 `release_recovery_required`、停止自动重试并人工清理。只有 Release 已公开且 assets/hash 完整才报告稳定发布成功。发布证据记录 commit、Node 24 精确版本、所有命令、测试报告、ruleset/bypass actor 检查结果、补偿演练和产物 hash。
