**评估基线**：2.1.0 当前工作区<br>
**评估日期**：2026-08-14<br>
**Git 基线**：`a4c27f6` 加评估时未提交改动<br>
**性质**：优先级草案，不是版本或日期承诺<br>
**原则来源**：[`docs/PROJECT-PRINCIPLES.md`](../PROJECT-PRINCIPLES.md)

## 结论

当前项目最强的部分是本地数据所有权、先保存后归档、可恢复写入和默认安全；这套可信底座必须保留。最弱的部分不是“功能还不够多”，而是收藏后的再次浮现、验证和长期回顾仍不完整，同时前端体量、真实浏览器自动化与部分旧文档已经落后于产品能力。

因此下一阶段不应优先继续增加内容平台或视觉模块，而应把工作流从：

```text
保存 → 研究 → 生成方案
```

补全为：

```text
保存 → 留存 → 研究 → 形成方案 → 验证结果 → 定期回顾
```

这是完整工作流的实施简写：“发现”发生在保存之前，“形成方案”是关联阶段的产物，“定期回顾”是回顾阶段的重复机制。

## 评估口径

- **强**：关键行为已经实现，并有自动化测试覆盖主要失败路径。
- **较强**：核心行为已实现，但生命周期、规模提示或自动化门禁仍有明显缺口。
- **部分**：只有部分路径可用，或仍依赖人工验收才能证明可靠。
- **证据快照**：`README.md`、`SECURITY.md`、`lib/`、`board.js`、CI 与发布清单；2026-08-14 实际运行 `npm run check` 为 29/29 测试文件通过。`npm run coverage` 只检查 4 个指定模块，不代表全项目覆盖率；4 个 scraper 文件使用固定夹具/Stub，不代表真实联网成功率。

主要证据入口：数据写入与恢复见 `lib/store.js`、`lib/schema.js`、`lib/migrate.js`、`lib/backup.js`、`lib/trash.js`；采集与留存见 `lib/capture.js`、`lib/archive.js`、`lib/archive-queue.js`；证据关联见 `lib/brainstorm.js`；安全边界见 `lib/auth.js`、`lib/safeurl.js`、`SECURITY.md`；测试与分发见 `package.json`、`.github/workflows/ci.yml`、`docs/RELEASE-CHECKLIST.md`。

## 取长补短

### 必须保留

- `DATA.md` 与 Markdown 档案作为用户可直接控制的事实源。
- save-first、archive-second，以及“增强失败不撤销收藏”。
- 原子写、备份、稳定 UID、回收站和重启可恢复队列。
- 不依赖外部 AI/API Key 的核心研究与头脑风暴。
- 建议带证据、置信度与验证步骤，不以生成量代替可信度。
- 默认回环、拒绝私网抓取、外部入口最小权限。

### 需要补齐

1. **从采集型产品升级为回顾型产品**：让长期未研究、归档异常和需要复盘的内容自动回到视野。
2. **从生成方案升级为验证方案**：保存实验结果，区分待验证、有效和无效方案，让后续建议使用真实反馈。
3. **从有备份升级为可证明恢复**：容量预检、事务导入、自动回滚、校验清单和定期恢复演练。
4. **从人工验收升级为持续门禁**：浏览器交互、可访问性、Windows 成品和更广的风险模块进入自动化。
5. **从功能增长升级为结构增长**：保持原生技术栈，但拆分过大的前端职责和高频逐条请求。

- [x] 建立当前原则对照与优先级。
- [x] 新增受版本控制的 `docs/INDEX.md` 文档入口，不再依赖被忽略的旧重复文档。
- [x] 在 README、贡献指南、发布清单和历史计划中接入原则。

### B. 可信恢复与待处理中心（下一优先级）

详细合同、实施依赖和发布门禁见 [v2.2.0 可信恢复与回顾升级计划](2026-08-14-v2.2-trusted-recovery-review-plan.md)。

- [x] **B1（最高）**：主数据与条目档案导入增加全局字节、磁盘空间、事务清单和失败自动回滚。
- [x] **B2**：为条目设计 `createdAt`、`lastStudiedAt`、`nextReviewAt` 的兼容格式、默认阈值与迁移测试；默认只在应用内浮出，不制造系统通知噪声。
- [x] **B3（依赖 B2）**：新增“待处理中心”，聚合未研究、归档失败、久未回顾和未完成行动项，并公开排序依据。
- [x] **B4**：增加本地归档文件完整性巡检；它只验证存在、可读和校验一致，不主动重复访问外站，也不声称来源内容最新。

**验收**：模拟每个导入阶段故障后均自动回到导入前状态；旧数据迁移前后条目和附件计数一致；待处理中心的每个结果都能说明命中规则并被用户延后或完成。

### C. 采集与决策反馈

- [ ] 统一手机/远程采集契约：只允许新增 URL，具备去重、限流、来源记录和最小权限。
- [ ] 将现有企业微信、钉钉作为适配器；不绑定未经支持的微信个人号自动化。
- [ ] 头脑风暴方案增加验证状态、结果、复盘日期和来源证据覆盖率。
- [ ] 让已验证结论参与后续本地推荐，失败方案同样保留为证据。

**验收**：远程入口无法读取或修改其他数据；任一保存方案都能记录真实验证结果并回到来源条目。

### D. 规模与工程门禁

- [x] 批量读取归档状态，避免每条一次请求撞到默认限流。
- [ ] 为搜索建立可失效的本地缓存（已完成），为成功队列增加安全压缩策略（待完成）。
- [ ] 分拆浏览器端 data、entry、archive、brainstorm 模块，不改变无框架运行方式。
- [ ] 为收藏、研究、截图、回收站、备份五条主路径增加真实浏览器测试。
- [ ] 在 Windows CI runner 构建并 smoke 成品（已完成）；根据商业交付量评估代码签名（待评估）。

**验收**：1000 条数据下不发生请求风暴；关键 UI 回归不再只依赖源码字符串；发布成品由 CI 生成并验证。

## 暂不做

- 云同步、多人协作、账号和订阅体系。
- 强制 AI 总结或要求用户配置 API Key。
- 为扩大“支持平台数”而加入缺乏维护边界的抓取器。
- 在研究与回顾闭环验证前重做技术栈或引入大型前端框架。

## 复核方式

每个稳定版本发布前更新本文件的“评估基线”和状态，只记录可验证结果。成功率、性能和首次使用时间若没有样本或自动化报告，继续标为目标，不能写成已达成事实。
